## 第 1 题

**问题：** 请你结合 HJMedia，概括一次 RTMP 推流从采集到网络发送的完整链路。请说明每个阶段的职责，以及图（Graph）和节点（Node）各自承担什么作用。

**回答：**

> 完整的链路：视频方面摄像头采集数据，RTE处理，编码为flv，得到视频帧。音频方面，麦克风音频采集，音频格式转换器，编码为acc。将编码后的音频ACC格式的数据和FLV格式的视频数据交织。最后通过RTMP推流出去。

**点评：**

- 整体方向正确：采集 → 处理 → 编码 → 交织/封装 → RTMP 发送。
- RTE 是可选的实时渲染处理链，不是推流的必经环节；也可能接入人脸检测、Faceu 或 Prio 等前处理。
- 视频编码产物通常是 H.264/H.265 等编码帧，不是 FLV；音频是 AAC。FLV 是复用/封装阶段将音视频包组织起来的容器格式。
- 题目要求的 Graph 与 Node 尚未说明：Graph 负责按场景组装、连接并驱动整条推流链路；Node 是具体处理单元，承担采集、处理、编码、封装或发送等单一职责，并借助帧队列连接、调度与反压机制传递数据。

**参考答案：**

一次 RTMP 推流可概括为以下链路：

1. **采集**：摄像头采集原始视频帧，麦克风采集原始 PCM 音频帧。
2. **可选前处理**：视频可经过人脸检测、Faceu、Prio 或 RTE 等处理；音频可进行重采样、声道/采样格式转换、音量或特效处理，使输入满足编码器要求。
3. **编码**：视频编码器把原始视频帧压缩为 H.264/H.265 等编码包；音频编码器将 PCM 压缩为 AAC 等编码包。
4. **复用与交织**：Muxer 按时间戳将音视频编码包交织，封装为适合 RTMP 传输的 FLV Tag/消息，维持正确的 A/V 时间顺序。
5. **网络发送**：RTMP 输出模块完成握手、连接、发布流，并将封装后的音视频消息发送到流媒体服务器。

在 HJMedia 中，`HJGraphPusher` 负责根据推流场景创建并连接采集、处理、编码、封装和网络输出等节点，统一管理初始化、启动、停止和生命周期。每个 Node 则只处理一个明确阶段，并通过 `connect(A, B, capacity)` 建立数据边。帧缓冲由消费者 B 管理；上游 Node 投递前检查下游是否已满，从而形成反压。节点由调度器异步执行，按 DriveType 在生产或消费后继续唤醒相邻节点，最终将整条链路组织成可并发运行的媒体处理图。

## 第 2 题

**问题：** 在 HJMedia 中，`connect(A, B, capacity)` 建立连接后，帧缓冲区归生产者 A 还是消费者 B 管理？为什么这样设计？

**回答：**

> 帧缓冲区是消费者必然管理的，这样是因为“花椒一点儿”这个项目采用的是反压机制。只有消费者消费了一帧，生产者才能往帧缓冲区中写入新的一帧。

**点评：**

- 回答抓住了核心：缓冲区由消费者管理，队列满时会形成反压。
- “只有消费者消费一帧，生产者才能写一帧”不够准确。生产者只要发现下游消费者的缓冲区未满，就可以继续 `deliver()`；只有队列满时才暂停生产。
- 消费者 `pop()` 后，在 `HJNODE_DRIVE_PRE` 驱动下会唤醒前驱继续生产。因此，消费者的消费速度与缓冲容量共同限制上游速率。

**参考答案：**

`connect(A, B, capacity)` 会在消费者 B 侧创建并管理来自生产者 A 的 `HJMediaStorage`，保存于 B 的 `m_inStorages`。这样由消费者定义每条输入边的缓存容量，能按自身处理能力控制缓冲；A 在投递前通过 `B->isFull()` 感知是否已满，满时停止继续投递，形成反压。B 消费帧后，若采用 `HJNODE_DRIVE_PRE`，会调度前驱 A 恢复生产。使用这种模型可以限制内存占用，也能让慢消费者自然限制上游生产速率。

## 第 3 题

**问题：** 在 HJMedia 的媒体处理图中，Node 之间通过 `connect(A, B, capacity)` 建立前驱/后继关系。假设 A 与 B 都用 `shared_ptr` 强引用彼此的邻接节点：当 Graph 停止并释放自身持有的节点后，可能发生什么内存问题？为什么 `HJMediaNode` 的邻接节点通常使用 `weak_ptr`？请进一步说明：运行时需要访问相邻节点时，应该如何安全地使用 `weak_ptr`？

**回答：**

> 第1点：如果使用 `shared_ptr` 强引用，可能会导致循环引用的问题，导致 Node 无法释放。使用 `weak_ptr` 可以解决循环引用的问题。

**阶段点评：**

- 正确。A 与 B（或图中的多个节点）相互持有 `shared_ptr` 时，引用计数无法降为 0；即使 Graph 已释放自己持有的节点，Node 仍会因环状强引用而泄漏。
- `weak_ptr` 不增加引用计数，因此适合表达“可访问的拓扑关系”，而非“所有权关系”。Node 的实际所有权应由 Graph 或其节点容器持有。
- 还需说明：使用 `weak_ptr` 时如何取得并验证相邻 Node 的临时强引用。

**补充回答：**

> 如果 Node 已经销毁，`weak_ptr` 就没办法再访问到它。

**补充点评：**

- 正确。被管理对象销毁后，`weak_ptr` 本身仍可存在，但它已过期，不能再解引用访问 Node。
- 正确写法是调用 `lock()`，仅在成功得到临时 `shared_ptr` 后访问节点；不要先 `expired()` 再访问，因为两步之间对象仍可能在其他线程中销毁。

```cpp
auto nextNode = m_nextNode.lock();
if (!nextNode) {
    return; // 相邻 Node 已销毁或正在销毁
}
nextNode->proRun();
```

**参考答案：**

Graph（或其节点容器）应以 `shared_ptr` 持有 Node，表示明确的生命周期所有权；Node 的前驱/后继仅表示图拓扑，通常保存 `weak_ptr`。如果 A、B 互相以 `shared_ptr` 保存邻接关系，就会产生循环引用，Graph 停止并释放其强引用后，A、B 的引用计数仍不为 0，造成 Node 及其关联资源无法释放。

访问邻接节点时，先调用 `weak_ptr::lock()` 取得临时 `shared_ptr`，再判断是否为空；只有成功时才能访问该节点。例如：`if (auto next = m_nextNode.lock()) { /* 安全使用 next */ }`。若 `lock()` 失败，说明节点已经被销毁或正在销毁，应跳过访问或结束当前处理，绝不能解引用失效的弱引用。

## 第 4 题

**问题：** HJMedia 的 `HJMediaNode` 使用 `m_driveType` 控制数据流的调度方向。请说明 `HJNODE_DRIVE_NEXT` 与 `HJNODE_DRIVE_PRE` 分别在什么时机、向哪个方向唤醒节点；并解释为什么音视频渲染节点通常只使用 `HJNODE_DRIVE_PRE`。

**回答：**

> 当采集有数据以后，会唤醒 `HJNODE_DRIVE_NEXT` 节点，当消费者消费 1 帧数据之后，会通知前置节点。因为这个项目采用的是反压的方式。

**点评：**

- 主线正确：生产侧完成投递后推进后续处理；消费侧取走帧后向上游发出可继续生产的信号，二者共同实现反压下的按需调度。
- 表述上，`HJNODE_DRIVE_NEXT` 不是“唤醒一个名为 DRIVE_NEXT 的节点”。它表示当前 Node 在 `deliver()` 后异步调度**自身**继续生产；而 `HJNODE_DRIVE_PRE` 表示当前 Node 在 `pop()` 消费帧后唤醒**前驱节点**继续生产。
- 还遗漏了渲染节点的原因：渲染节点是终端消费者，不产生供下游继续消费的媒体帧，因此通常只需要在消费后向前驱拉取更多数据；若开启 `DRIVE_NEXT`，会产生没有实际下游需求的额外自调度与 CPU 唤醒。

**参考答案：**

- `HJNODE_DRIVE_NEXT`：当前 Node 成功 `deliver()` 一帧给下游后，异步调度自身再次执行，以便在下游仍有容量时持续生产下一帧。这适合采集、解码、编码等主动生产型节点。
- `HJNODE_DRIVE_PRE`：当前 Node 通过 `pop()` 消费输入帧后，唤醒前驱 Node，使前驱知道下游腾出了缓存空间，可以继续生产。这是反压恢复的关键。
- 编解码等中间节点通常同时具备两种驱动：既要在产出后继续生产，也要在消费输入后向上游索取数据。音视频渲染节点是末端的纯消费者，通常只设 `HJNODE_DRIVE_PRE`；它渲染一帧后只需拉动前驱补帧，不需要 `DRIVE_NEXT` 自行产生下游数据，从而避免无效唤醒。

## 第 5 题

**问题：** HJMedia 的 Node 通常通过调度器异步执行，并使用 `m_isBusy` 防止重入。请说明：如果没有 `m_isBusy`，同一个 Node 的 `proRun()` 可能出现什么并发问题？仅给 `proRun()` 加互斥锁，是否就完全等价于 `m_isBusy` 的作用？为什么？

**回答：**

> 这个问题我不太清楚。

**点评：**

- 这一题的关键是区分“互斥执行”与“防止重复调度/重入”。`m_isBusy` 不只是锁的替代品，而是 Node 的任务状态标记。

**参考答案：**

同一个 Node 可能因上游投递、下游消费、定时调度等多个事件被多次请求执行。若没有 `m_isBusy`，多个调度任务可能同时或重叠进入 `proRun()`，从同一输入队列重复 `pop()`、向下游重复 `deliver()`，或同时修改 EOF、暂停、生命周期等状态，造成帧丢失/重复、状态错乱和数据竞争。

`m_isBusy` 的作用是任务去重与重入防护：Node 已在执行或已被调度时，新的触发不再重复投递同一项工作；当前 `proRun()` 结束时通常借助 `HJOnceToken` 将 busy 状态复位。这样多个触发会被合并为一次有效执行，避免线程池积压大量无效任务。

仅给 `proRun()` 加互斥锁并不完全等价。互斥锁只能保证多个任务不会**同时**进入函数体：第一个任务执行时，其余任务会阻塞；之后它们仍会依次执行，造成任务堆积、无效唤醒和额外锁竞争。`m_isBusy` 则在任务入口或调度阶段直接拒绝/合并重复执行请求，表达的是“当前 Node 已经有一项工作在进行”的调度语义。实际实现中，二者可配合：锁保护共享状态，`m_isBusy` 控制任务是否需要被调度。

## 第 6 题

**问题：** 在一条“解复用 → 解码 → 渲染”的媒体图中，输入源到达 EOF 后，为什么不能由解复用节点立刻销毁整条链路？请说明 EOF 帧应如何沿下游传播，以及一个 Node 在什么条件下才能认为自己真正处理完毕。

**回答：**

> 输入源到达 EOF 后，并不意味着整条链路中没有待处理的数据了，EOF 帧数据流向下传播，一个 Node 节点只有在接收到 EOF 帧，以及自己的媒体队列为空后，才会认为自己真正处理完毕了。

**点评：**

- 正确。EOF 表示上游不再产生新输入，不表示解码器、Node 队列或渲染器已经排空。
- 还可补充：解码器在收到 EOF 后需要执行 flush，输出其内部缓存的尾帧；否则结尾的音视频帧可能丢失。
- 对有多个后继的 Node，还需等所有后继都已完成 EOF 处理，才能安全地将自身标记为 EOF 并进入最终清理，避免某一路仍在消费数据时提前释放资源。

**参考答案：**

解复用器读到 EOF 仅说明它无法再读出新的编码包；下游可能仍缓存有编码包、解码器内部重排序帧，或渲染器尚未播放的原始帧。若此时立即销毁 Graph，会截断尾帧并可能让异步任务访问已释放资源。

正确方式是把 EOF 作为特殊媒体帧沿 DAG 向下游 `deliver()`：解码节点收到 EOF 后先 flush 解码器，将内部剩余帧全部输出，再向下游发送 EOF；渲染节点收到 EOF 后继续播放/渲染已缓存帧，直到队列排空。一个 Node 只有在收到上游 EOF、处理并输出自身的所有残留数据，且其所有后继均已完成 EOF 时，才能将自己标记为完成。`done()` 等收尾操作应通过调度器同步等待相关异步任务完成后，再释放资源。

## 第 7 题

**问题：** 点播播放器执行 Seek 时，为什么需要先让音频和视频渲染节点进入 `setPreFlush(true)` 状态，再清理队列并跳转到新的时间点？如果跳转前不这样做，用户可能看到或听到什么现象？

**回答：**

> 这样做是为了让渲染节点之前的节点清空媒体队列。然后渲染节点自身，再清理队列并跳转到新的时间。如果不这样做，可能导致 Seek 前后播放的音视频出现混乱。

**点评：**

- 方向正确：Seek 的目标是清除旧时间轴的数据，并避免旧数据与新时间点的数据交叉播放。
- 更准确地说，`setPreFlush(true)` 的直接职责是先让音视频渲染节点进入预刷新/抑制输出状态；在上游暂停、清队列、解复用跳转和重新解码的过渡窗口内，渲染器不会继续消费并输出残留旧帧。
- 若不做预刷新，渲染线程可能在清理尚未完成时继续播放旧 PCM 或显示旧视频帧，造成画面回跳、旧画面闪现、旧声音残留，甚至短暂的音画不同步。

**参考答案：**

Seek 是跨线程状态切换：解复用器要定位到新时间点，解码器与 Node 队列要丢弃旧时间轴数据，而渲染线程可能仍在独立地消费旧帧。先对音频、视频渲染节点设置 `setPreFlush(true)`，可在切换期间阻止其继续输出旧帧；之后再暂停/清理相关队列、flush 解码器、执行 Seek，并从新位置重新解复用和解码。待新时间点的首批有效帧准备好后，解除预刷新并恢复渲染。

若省略这一步，旧缓存帧可能与新位置的帧交错输出：视频会闪回 Seek 前画面或短暂跳帧，音频会残留旧声音、爆音，且两条链路清空速度不同还会加剧 A/V 不同步。

## 第 8 题

**问题：** 音视频播放中，为什么通常以音频时钟作为主时钟？当视频帧的显示时间戳（PTS）明显落后于音频时钟时，播放器通常如何处理这帧视频？反过来，视频 PTS 领先时又应如何处理？

**回答：**

> 这个问题我不太清楚。

**点评：**

- 需要掌握的核心是：音频输出由声卡按稳定节奏持续播放，随意暂停或丢弃音频容易产生卡顿、爆音，因此通常选音频时钟作为主时钟；视频通过“等待或丢帧”去追赶音频。

**参考答案：**

音频通常作为主时钟，因为音频设备以固定采样率持续消耗 PCM，节奏稳定；频繁调整音频会带来明显的卡顿、爆音或音调异常。视频更适合通过改变显示时机来同步。

播放器比较视频帧 PTS 与当前音频时钟：

- 若视频 PTS 明显**落后**音频时钟，说明这帧已过显示时机，通常丢弃该视频帧（必要时连续丢到接近音频时钟的关键帧/合适帧），以追赶音频。
- 若视频 PTS **领先**音频时钟，说明视频来早了，渲染器应延迟显示或短暂等待，直到音频时钟接近该 PTS 再渲染。
- 若差值处于允许阈值内，则按正常节奏显示。阈值通常会结合帧率、缓冲状态和播放速度设定，避免微小抖动导致频繁等待或丢帧。

## 第 9 题

**问题：** 为什么 HJMedia 的音频帧队列容量通常按“采样率 × 时间窗口 ÷ 每帧采样数”估算，而视频帧队列容量按“帧率 × 时间窗口”估算？请分别解释两个公式中各项的含义。

**回答：**

> 在音频帧队列中，采样率代表 1 秒钟内有多少个采样点，乘以时间窗口，除以每帧采样数，就能够算出音频帧队列的容量了。帧率代表每秒钟播放多少帧，乘以时间窗口就代表了视频帧队列的容量大致是多少。

**点评：**

- 正确。你已准确说明这两个公式都是按目标缓存时长估算队列中需要容纳的“帧数”。
- 可进一步强调单位：采样率的单位是 samples/s，乘以秒得到 samples，再除以 samples/frame，结果是 audio frames；视频帧率的单位是 frames/s，乘以秒直接得到 video frames。
- HJMedia 中音频在多后继场景还会按约 1.2 倍弹性扩容，以缓冲多个下游消费速度不同带来的波动。

**参考答案：**

队列容量的目的不是固定保存多少字节，而是保存大约固定时长（例如默认约 2 秒）的媒体数据，以平衡抗抖动能力、延迟和内存占用。

- 视频：`capacity ≈ frameRate × timeCapacity`。`frameRate` 是每秒视频帧数（frames/s），`timeCapacity` 是希望缓存的秒数（s），结果就是视频队列应保存的帧数。例如 30 fps、2 s，容量约为 60 帧。
- 音频：`capacity ≈ sampleRate × timeCapacity ÷ samplesPerFrame`。`sampleRate` 是每秒采样数（samples/s）；乘以缓存秒数得到目标采样总数；再除以每个音频帧包含的采样数（samples/frame），得到应缓存的音频帧数。例如 48 kHz、每帧 1024 samples、2 s，容量约为 `48000 × 2 ÷ 1024 ≈ 94` 帧。

以时间而不是固定帧数估算，能适配不同帧率、采样率和音频帧大小；多后继时音频队列还可适当扩容以应对消费节奏差异。

## 第 10 题

**问题：** HJMedia Plugin 通常遵循 `init → start → process → stop → release` 生命周期。请分别说明 `init`、`start`、`stop` 与 `release` 的职责差异；为什么不能在 Plugin 尚未 ready 时直接调用 `process`？

**回答：**

> 这个问题我不太清楚。

**点评：**

- 这题的关键是区分“创建资源”“开始运行”“停止处理”和“销毁资源”。Plugin 的状态机决定 Graph 何时可以安全投递媒体帧。

**参考答案：**

Plugin 的生命周期可按职责理解：

1. **`init`：创建并配置。** 读取输入参数，创建编解码器、音频设备、线程、缓存或平台句柄等资源，设置格式/回调/输入输出关系，并将状态推进到可初始化或等待 ready 的阶段。某些平台资源（例如音频渲染器）可能异步完成初始化，所以 `init` 返回成功不一定代表立刻可处理帧。
2. **`start`：开始运行。** 在资源已 ready 后启动设备、工作线程或内部任务循环，使 Plugin 进入实际处理数据的运行状态；例如启动采集、启动音频输出或允许编码器开始工作。
3. **`process`：处理一帧或一批媒体数据。** 它依赖已经完成的格式协商、资源分配和运行状态，执行解码、编码、重采样、渲染或转发，并处理普通帧、flush、EOF 等控制帧。
4. **`stop`：停止运行但保留可复用资源。** 停止设备回调、工作线程和继续接收/输出的行为，处理必要的收尾或排空；通常不立即销毁全部对象，以便后续可能重新 `start`。
5. **`release`：最终释放。** 释放 `init` 创建的平台句柄、编解码上下文、缓冲区和线程等资源，解除回调与引用，使 Plugin 不再可用，之后若要再次使用应重新 `init`。

不能在 Plugin 尚未 ready 时调用 `process`，因为此时依赖的资源可能尚未创建完成或尚未进入可运行状态：例如编码器参数/输出格式尚未确定、音频设备尚未打开、回调尚未注册、内部队列或线程尚未就绪。直接处理可能返回错误、丢帧、访问空对象，或与异步初始化发生竞态。Graph 应遵循状态机，仅在 Plugin ready 且已按需要 start 后投递媒体帧。

## 第 11 题

**问题：** 在 RTMP 推流的音频链路中，为什么麦克风采集到的 PCM 往往不能直接交给 AAC 编码器，而需要先经过重采样或音频格式转换？请至少列出三类可能需要统一的音频参数。

**回答：**

> 这个问题我不太清楚。

**点评：**

- 要点是：PCM 只是原始音频数据的统称，并不代表其采样率、声道数、采样格式和每帧样本数已经满足 AAC 编码器的输入约束。

**参考答案：**

麦克风采集的 PCM 不能默认直接送入 AAC 编码器，因为“PCM”只说明数据未压缩；不同设备和平台采集到的 PCM 参数可能不同，而 AAC 编码器通常只接受某些确定的输入格式。编码前必须把采集端参数统一为编码器配置要求，否则会出现初始化失败、音速/音调异常、声道错乱、噪声或时间戳不连续等问题。

常见需要统一的参数至少包括：

1. **采样率（sample rate）**：如采集端为 44.1 kHz，而推流 AAC 编码配置为 48 kHz，就要重采样。采样率不同意味着每秒样本数不同，直接交给编码器会使媒体时长和声音速度解释错误。
2. **声道数与声道布局（channels / channel layout）**：例如单声道麦克风采集，而编码器输出要求双声道；需要做单声道复制、混音或声道布局转换。声道不匹配会导致左右声道异常、音量问题或编码器拒绝输入。
3. **采样格式（sample format）**：采集数据可能是 `S16`、`S32`、`float`，也可能是交错（interleaved）或平面（planar）布局；编码器可能要求特定格式，如浮点平面数据。格式转换负责样本精度、数据排列和字节布局的适配。

还常需要处理：

- **每个编码帧的采样数（samples per frame）**：AAC 常以固定数量（常见为 1024）采样组成一个编码帧；采集回调给出的样本数可能不刚好等于它，需要通过 FIFO 累积或拆分。
- **时间戳（PTS）**：重采样后要按输出采样率重新连续地计算 PTS，保证音频播放时长与视频同步。

因此典型流程是：麦克风 PCM → 重采样/声道与采样格式转换 → FIFO 对齐 AAC 所需帧大小 → AAC 编码 → 复用为 RTMP/FLV 音频消息。
