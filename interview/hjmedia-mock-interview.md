## 第 1 题

**问题：** 请你结合 HJMedia，概括一次 RTMP 推流从采集到网络发送的完整链路。请说明每个阶段的职责，以及图（Graph）和节点（Node）各自承担什么作用。

**回答：**

> 完整的链路：视频方面摄像头采集数据，RTE处理，编码为flv，得到视频帧。音频方面，麦克风音频采集，音频格式转换器，编码为acc。将编码后的音频ACC格式的数据和FLV格式的视频数据交织。最后通过RTMP推流出去。

**点评：**

- 整体方向正确：采集 → 处理 → 编码 → 交织/封装 → RTMP 发送。
- RTE 是可选的实时渲染处理链，不是推流的必经环节；也可能接入人脸检测、Faceu 或 Prio 等前处理。
- 视频编码产物通常是 H.264/H.265 等编码帧，不是 FLV；音频是 AAC。FLV 是复用/封装阶段将音视频包组织起来的容器格式。
- 题目要求的 Graph 与 Node 尚未说明：Graph 负责按场景组装、连接并驱动整条推流链路；Node 是具体处理单元，承担采集、处理、编码、封装或发送等单一职责，并借助帧队列连接、调度与反压机制传递数据。

**参考答案：**

花椒在 HarmonyOS 上的推流分为音视频两条链路：视频侧，`HJOGRenderWindowBridge` 创建 **OES 纹理**并将其与 `OH_NativeImage` 绑定，再把 `SurfaceId` 交给相机；相机写入 `Surface` 后，通过 `OH_NativeImage_UpdateSurfaceImage()` 将最新画面关联到 OES 纹理，RTE 中的 `HJRteComDrawCopyOESFBO` 再把它转换成 **RGBA 2D 纹理**。灰度、模糊、镜像和 Faceu 等可选效果继续处理 2D 纹理，最终由 `TargetEncoder` 将纹理绘制到编码器 Surface，经硬编码得到 **Annex B 格式的 H.264/H.265 ES**。音频侧，麦克风采集 **S16LE PCM**，经过 `HJPluginAudioResampler` 转换格式并按 1024 个采样点组帧，再由 `HJPluginFDKAACEncoder` 编码成 **AAC ES**。最后，`HJPluginAVInterleave` 按 DTS 交织音视频编码包，`HJPluginRTMPMuxer` 通过 `HJESParser` 将 Annex B 起始码转换为 4 字节 NAL 长度前缀（H.264 为 AVCC 格式，H.265 同样使用长度前缀），再封装成 **FLV Tag**并通过 librtmp 发送到服务器；RTE Graph 负责视频纹理处理，`HJGraphPusher` 负责音视频编码、交织、发送和生命周期管理。

## 第 2 题

**问题：** 在 HJMedia 中，`connect(A, B, capacity)` 建立连接后，帧缓冲区归生产者 A 还是消费者 B 管理？为什么这样设计？

**回答：**

> 帧缓冲区是消费者必然管理的，这样是因为“花椒一点儿”这个项目采用的是反压机制。只有消费者消费了一帧，生产者才能往帧缓冲区中写入新的一帧。

**点评：**

- 回答抓住了核心：缓冲区由消费者管理，队列满时会形成反压。
- “只有消费者消费一帧，生产者才能写一帧”不够准确。生产者只要发现下游消费者的缓冲区未满，就可以继续 `deliver()`；只有队列满时才暂停生产。
- 消费者 `pop()` 后，在 `HJNODE_DRIVE_PRE` 驱动下会唤醒前驱继续生产。因此，消费者的消费速度与缓冲容量共同限制上游速率。

**参考答案：**

`connect(A, B, capacity)` 会在消费者 B 侧创建并管理来自生产者 A 的 `HJMediaStorage`，保存于 B 的 `m_inStorages`。这样由消费者定义每条输入边的缓存容量，能按自身处理能力控制缓冲；A 在投递前通过 `B->isFull()` 感知是否已满，满时停止继续投递，形成反压。B 消费帧后，若采用 `HJNODE_DRIVE_PRE`，会调度前驱 A 恢复生产。使用这种模型可以限制内存占用，也能让慢消费者自然限制上游生产速率。

## 第 3 题

**问题：** 在 HJMedia 的媒体处理图中，Node 之间通过 `connect(A, B, capacity)` 建立前驱/后继关系。假设 A 与 B 都用 `shared_ptr` 强引用彼此的邻接节点：当 Graph 停止并释放自身持有的节点后，可能发生什么内存问题？为什么 `HJMediaNode` 的邻接节点通常使用 `weak_ptr`？请进一步说明：运行时需要访问相邻节点时，应该如何安全地使用 `weak_ptr`？

**回答：**

> 第1点：如果使用 `shared_ptr` 强引用，可能会导致循环引用的问题，导致 Node 无法释放。使用 `weak_ptr` 可以解决循环引用的问题。

**阶段点评：**

- 正确。A 与 B（或图中的多个节点）相互持有 `shared_ptr` 时，引用计数无法降为 0；即使 Graph 已释放自己持有的节点，Node 仍会因环状强引用而泄漏。
- `weak_ptr` 不增加引用计数，因此适合表达“可访问的拓扑关系”，而非“所有权关系”。Node 的实际所有权应由 Graph 或其节点容器持有。
- 还需说明：使用 `weak_ptr` 时如何取得并验证相邻 Node 的临时强引用。

**补充回答：**

> 如果 Node 已经销毁，`weak_ptr` 就没办法再访问到它。

**补充点评：**

- 正确。被管理对象销毁后，`weak_ptr` 本身仍可存在，但它已过期，不能再解引用访问 Node。
- 正确写法是调用 `lock()`，仅在成功得到临时 `shared_ptr` 后访问节点；不要先 `expired()` 再访问，因为两步之间对象仍可能在其他线程中销毁。

```cpp
auto nextNode = m_nextNode.lock();
if (!nextNode) {
    return; // 相邻 Node 已销毁或正在销毁
}
nextNode->proRun();
```

**参考答案：**

Graph（或其节点容器）应以 `shared_ptr` 持有 Node，表示明确的生命周期所有权；Node 的前驱/后继仅表示图拓扑，通常保存 `weak_ptr`。如果 A、B 互相以 `shared_ptr` 保存邻接关系，就会产生循环引用，Graph 停止并释放其强引用后，A、B 的引用计数仍不为 0，造成 Node 及其关联资源无法释放。

访问邻接节点时，先调用 `weak_ptr::lock()` 取得临时 `shared_ptr`，再判断是否为空；只有成功时才能访问该节点。例如：`if (auto next = m_nextNode.lock()) { /* 安全使用 next */ }`。若 `lock()` 失败，说明节点已经被销毁或正在销毁，应跳过访问或结束当前处理，绝不能解引用失效的弱引用。

## 第 4 题

**问题：** HJMedia 的 `HJMediaNode` 使用 `m_driveType` 控制数据流的调度方向。请说明 `HJNODE_DRIVE_NEXT` 与 `HJNODE_DRIVE_PRE` 分别在什么时机、向哪个方向唤醒节点；并解释为什么音视频渲染节点通常只使用 `HJNODE_DRIVE_PRE`。

**回答：**

> 当采集有数据以后，会唤醒 `HJNODE_DRIVE_NEXT` 节点，当消费者消费 1 帧数据之后，会通知前置节点。因为这个项目采用的是反压的方式。

**点评：**

- 主线正确：生产侧完成投递后推进后续处理；消费侧取走帧后向上游发出可继续生产的信号，二者共同实现反压下的按需调度。
- 表述上，`HJNODE_DRIVE_NEXT` 不是“唤醒一个名为 DRIVE_NEXT 的节点”。它表示当前 Node 在 `deliver()` 后异步调度**自身**继续生产；而 `HJNODE_DRIVE_PRE` 表示当前 Node 在 `pop()` 消费帧后唤醒**前驱节点**继续生产。
- 还遗漏了渲染节点的原因：渲染节点是终端消费者，不产生供下游继续消费的媒体帧，因此通常只需要在消费后向前驱拉取更多数据；若开启 `DRIVE_NEXT`，会产生没有实际下游需求的额外自调度与 CPU 唤醒。

**参考答案：**

- `HJNODE_DRIVE_NEXT`：当前 Node 成功 `deliver()` 一帧给下游后，异步调度自身再次执行，以便在下游仍有容量时持续生产下一帧。这适合采集、解码、编码等主动生产型节点。
- `HJNODE_DRIVE_PRE`：当前 Node 通过 `pop()` 消费输入帧后，唤醒前驱 Node，使前驱知道下游腾出了缓存空间，可以继续生产。这是反压恢复的关键。
- 编解码等中间节点通常同时具备两种驱动：既要在产出后继续生产，也要在消费输入后向上游索取数据。音视频渲染节点是末端的纯消费者，通常只设 `HJNODE_DRIVE_PRE`；它渲染一帧后只需拉动前驱补帧，不需要 `DRIVE_NEXT` 自行产生下游数据，从而避免无效唤醒。

## 第 5 题

**问题：** HJMedia 的 Node 通常通过调度器异步执行，并使用 `m_isBusy` 防止重入。请说明：如果没有 `m_isBusy`，同一个 Node 的 `proRun()` 可能出现什么并发问题？仅给 `proRun()` 加互斥锁，是否就完全等价于 `m_isBusy` 的作用？为什么？

**回答：**

> 这个问题我不太清楚。

**点评：**

- 这一题的关键是区分“互斥执行”与“防止重复调度/重入”。`m_isBusy` 不只是锁的替代品，而是 Node 的任务状态标记。

**参考答案：**

同一个 Node 可能因上游投递、下游消费、定时调度等多个事件被多次请求执行。若没有 `m_isBusy`，多个调度任务可能同时或重叠进入 `proRun()`，从同一输入队列重复 `pop()`、向下游重复 `deliver()`，或同时修改 EOF、暂停、生命周期等状态，造成帧丢失/重复、状态错乱和数据竞争。

`m_isBusy` 的作用是任务去重与重入防护：Node 已在执行或已被调度时，新的触发不再重复投递同一项工作；当前 `proRun()` 结束时通常借助 `HJOnceToken` 将 busy 状态复位。这样多个触发会被合并为一次有效执行，避免线程池积压大量无效任务。

仅给 `proRun()` 加互斥锁并不完全等价。互斥锁只能保证多个任务不会**同时**进入函数体：第一个任务执行时，其余任务会阻塞；之后它们仍会依次执行，造成任务堆积、无效唤醒和额外锁竞争。`m_isBusy` 则在任务入口或调度阶段直接拒绝/合并重复执行请求，表达的是“当前 Node 已经有一项工作在进行”的调度语义。实际实现中，二者可配合：锁保护共享状态，`m_isBusy` 控制任务是否需要被调度。

## 第 6 题

**问题：** 在一条“解复用 → 解码 → 渲染”的媒体图中，输入源到达 EOF 后，为什么不能由解复用节点立刻销毁整条链路？请说明 EOF 帧应如何沿下游传播，以及一个 Node 在什么条件下才能认为自己真正处理完毕。

**回答：**

> 输入源到达 EOF 后，并不意味着整条链路中没有待处理的数据了，EOF 帧数据流向下传播，一个 Node 节点只有在接收到 EOF 帧，以及自己的媒体队列为空后，才会认为自己真正处理完毕了。

**点评：**

- 正确。EOF 表示上游不再产生新输入，不表示解码器、Node 队列或渲染器已经排空。
- 还可补充：解码器在收到 EOF 后需要执行 flush，输出其内部缓存的尾帧；否则结尾的音视频帧可能丢失。
- 对有多个后继的 Node，还需等所有后继都已完成 EOF 处理，才能安全地将自身标记为 EOF 并进入最终清理，避免某一路仍在消费数据时提前释放资源。

**参考答案：**

解复用器读到 EOF 仅说明它无法再读出新的编码包；下游可能仍缓存有编码包、解码器内部重排序帧，或渲染器尚未播放的原始帧。若此时立即销毁 Graph，会截断尾帧并可能让异步任务访问已释放资源。

正确方式是把 EOF 作为特殊媒体帧沿 DAG 向下游 `deliver()`：解码节点收到 EOF 后先 flush 解码器，将内部剩余帧全部输出，再向下游发送 EOF；渲染节点收到 EOF 后继续播放/渲染已缓存帧，直到队列排空。一个 Node 只有在收到上游 EOF、处理并输出自身的所有残留数据，且其所有后继均已完成 EOF 时，才能将自己标记为完成。`done()` 等收尾操作应通过调度器同步等待相关异步任务完成后，再释放资源。

## 第 7 题

**问题：** 点播播放器执行 Seek 时，为什么需要先让音频和视频渲染节点进入 `setPreFlush(true)` 状态，再清理队列并跳转到新的时间点？如果跳转前不这样做，用户可能看到或听到什么现象？

**回答：**

> 这样做是为了让渲染节点之前的节点清空媒体队列。然后渲染节点自身，再清理队列并跳转到新的时间。如果不这样做，可能导致 Seek 前后播放的音视频出现混乱。

**点评：**

- 方向正确：Seek 的目标是清除旧时间轴的数据，并避免旧数据与新时间点的数据交叉播放。
- 更准确地说，`setPreFlush(true)` 的直接职责是先让音视频渲染节点进入预刷新/抑制输出状态；在上游暂停、清队列、解复用跳转和重新解码的过渡窗口内，渲染器不会继续消费并输出残留旧帧。
- 若不做预刷新，渲染线程可能在清理尚未完成时继续播放旧 PCM 或显示旧视频帧，造成画面回跳、旧画面闪现、旧声音残留，甚至短暂的音画不同步。

**参考答案：**

Seek 是跨线程状态切换：解复用器要定位到新时间点，解码器与 Node 队列要丢弃旧时间轴数据，而渲染线程可能仍在独立地消费旧帧。先对音频、视频渲染节点设置 `setPreFlush(true)`，可在切换期间阻止其继续输出旧帧；之后再暂停/清理相关队列、flush 解码器、执行 Seek，并从新位置重新解复用和解码。待新时间点的首批有效帧准备好后，解除预刷新并恢复渲染。

若省略这一步，旧缓存帧可能与新位置的帧交错输出：视频会闪回 Seek 前画面或短暂跳帧，音频会残留旧声音、爆音，且两条链路清空速度不同还会加剧 A/V 不同步。

## 第 8 题

**问题：** 音视频播放中，为什么通常以音频时钟作为主时钟？当视频帧的显示时间戳（PTS）明显落后于音频时钟时，播放器通常如何处理这帧视频？反过来，视频 PTS 领先时又应如何处理？

**回答：**

> 这个问题我不太清楚。

**点评：**

- 需要掌握的核心是：音频输出由声卡按稳定节奏持续播放，随意暂停或丢弃音频容易产生卡顿、爆音，因此通常选音频时钟作为主时钟；视频通过“等待或丢帧”去追赶音频。

**参考答案：**

音频通常作为主时钟，因为音频设备以固定采样率持续消耗 PCM，节奏稳定；频繁调整音频会带来明显的卡顿、爆音或音调异常。视频更适合通过改变显示时机来同步。

播放器比较视频帧 PTS 与当前音频时钟：

- 若视频 PTS 明显**落后**音频时钟，说明这帧已过显示时机，通常丢弃该视频帧（必要时连续丢到接近音频时钟的关键帧/合适帧），以追赶音频。
- 若视频 PTS **领先**音频时钟，说明视频来早了，渲染器应延迟显示或短暂等待，直到音频时钟接近该 PTS 再渲染。
- 若差值处于允许阈值内，则按正常节奏显示。阈值通常会结合帧率、缓冲状态和播放速度设定，避免微小抖动导致频繁等待或丢帧。

## 第 9 题

**问题：** 为什么 HJMedia 的音频帧队列容量通常按“采样率 × 时间窗口 ÷ 每帧采样数”估算，而视频帧队列容量按“帧率 × 时间窗口”估算？请分别解释两个公式中各项的含义。

**回答：**

> 在音频帧队列中，采样率代表 1 秒钟内有多少个采样点，乘以时间窗口，除以每帧采样数，就能够算出音频帧队列的容量了。帧率代表每秒钟播放多少帧，乘以时间窗口就代表了视频帧队列的容量大致是多少。

**点评：**

- 正确。你已准确说明这两个公式都是按目标缓存时长估算队列中需要容纳的“帧数”。
- 可进一步强调单位：采样率的单位是 samples/s，乘以秒得到 samples，再除以 samples/frame，结果是 audio frames；视频帧率的单位是 frames/s，乘以秒直接得到 video frames。
- HJMedia 中音频在多后继场景还会按约 1.2 倍弹性扩容，以缓冲多个下游消费速度不同带来的波动。

**参考答案：**

队列容量的目的不是固定保存多少字节，而是保存大约固定时长（例如默认约 2 秒）的媒体数据，以平衡抗抖动能力、延迟和内存占用。

- 视频：`capacity ≈ frameRate × timeCapacity`。`frameRate` 是每秒视频帧数（frames/s），`timeCapacity` 是希望缓存的秒数（s），结果就是视频队列应保存的帧数。例如 30 fps、2 s，容量约为 60 帧。
- 音频：`capacity ≈ sampleRate × timeCapacity ÷ samplesPerFrame`。`sampleRate` 是每秒采样数（samples/s）；乘以缓存秒数得到目标采样总数；再除以每个音频帧包含的采样数（samples/frame），得到应缓存的音频帧数。例如 48 kHz、每帧 1024 samples、2 s，容量约为 `48000 × 2 ÷ 1024 ≈ 94` 帧。

以时间而不是固定帧数估算，能适配不同帧率、采样率和音频帧大小；多后继时音频队列还可适当扩容以应对消费节奏差异。

**问题：** HJMedia Plugin 通常遵循 `init → start → process → stop → release` 生命周期。请分别说明 `init`、`start`、`stop` 与 `release` 的职责差异；为什么不能在 Plugin 尚未 ready 时直接调用 `process`？

> 这个问题我不太清楚。

**点评：**

- 这题的关键是区分“创建资源”“开始运行”“停止处理”和“销毁资源”。Plugin 的状态机决定 Graph 何时可以安全投递媒体帧。

**参考答案：**

Plugin 的生命周期可按职责理解：

1. **`init`：创建并配置。** 读取输入参数，创建编解码器、音频设备、线程、缓存或平台句柄等资源，设置格式/回调/输入输出关系，并将状态推进到可初始化或等待 ready 的阶段。某些平台资源（例如音频渲染器）可能异步完成初始化，所以 `init` 返回成功不一定代表立刻可处理帧。
2. **`start`：开始运行。** 在资源已 ready 后启动设备、工作线程或内部任务循环，使 Plugin 进入实际处理数据的运行状态；例如启动采集、启动音频输出或允许编码器开始工作。
3. **`process`：处理一帧或一批媒体数据。** 它依赖已经完成的格式协商、资源分配和运行状态，执行解码、编码、重采样、渲染或转发，并处理普通帧、flush、EOF 等控制帧。
4. **`stop`：停止运行但保留可复用资源。** 停止设备回调、工作线程和继续接收/输出的行为，处理必要的收尾或排空；通常不立即销毁全部对象，以便后续可能重新 `start`。
5. **`release`：最终释放。** 释放 `init` 创建的平台句柄、编解码上下文、缓冲区和线程等资源，解除回调与引用，使 Plugin 不再可用，之后若要再次使用应重新 `init`。

不能在 Plugin 尚未 ready 时调用 `process`，因为此时依赖的资源可能尚未创建完成或尚未进入可运行状态：例如编码器参数/输出格式尚未确定、音频设备尚未打开、回调尚未注册、内部队列或线程尚未就绪。直接处理可能返回错误、丢帧、访问空对象，或与异步初始化发生竞态。Graph 应遵循状态机，仅在 Plugin ready 且已按需要 start 后投递媒体帧。

## 第 11 题

**问题：** 在 RTMP 推流的音频链路中，为什么麦克风采集到的 PCM 往往不能直接交给 AAC 编码器，而需要先经过重采样或音频格式转换？请至少列出三类可能需要统一的音频参数。

**回答：**

> 这个问题我不太清楚。

**点评：**

- 要点是：PCM 只是原始音频数据的统称，并不代表其采样率、声道数、采样格式和每帧样本数已经满足 AAC 编码器的输入约束。

**参考答案：**

麦克风采集的 PCM 不能默认直接送入 AAC 编码器，因为“PCM”只说明数据未压缩；不同设备和平台采集到的 PCM 参数可能不同，而 AAC 编码器通常只接受某些确定的输入格式。编码前必须把采集端参数统一为编码器配置要求，否则会出现初始化失败、音速/音调异常、声道错乱、噪声或时间戳不连续等问题。

常见需要统一的参数至少包括：

1. **采样率（sample rate）**：如采集端为 44.1 kHz，而推流 AAC 编码配置为 48 kHz，就要重采样。采样率不同意味着每秒样本数不同，直接交给编码器会使媒体时长和声音速度解释错误。
2. **声道数与声道布局（channels / channel layout）**：例如单声道麦克风采集，而编码器输出要求双声道；需要做单声道复制、混音或声道布局转换。声道不匹配会导致左右声道异常、音量问题或编码器拒绝输入。
3. **采样格式（sample format）**：采集数据可能是 `S16`、`S32`、`float`，也可能是交错（interleaved）或平面（planar）布局；编码器可能要求特定格式，如浮点平面数据。格式转换负责样本精度、数据排列和字节布局的适配。

还常需要处理：

- **每个编码帧的采样数（samples per frame）**：AAC 常以固定数量（常见为 1024）采样组成一个编码帧；采集回调给出的样本数可能不刚好等于它，需要通过 FIFO 累积或拆分。
- **时间戳（PTS）**：重采样后要按输出采样率重新连续地计算 PTS，保证音频播放时长与视频同步。

因此典型流程是：麦克风 PCM → 重采样/声道与采样格式转换 → FIFO 对齐 AAC 所需帧大小 → AAC 编码 → 复用为 RTMP/FLV 音频消息。

## 第 12 题

**问题：** 在 HJMedia 的 RTE 渲染图中，RTE 与相机、图片这两类输入源的职责边界是如何划分的？它们分别以什么数据形式进入 RTE，进入图后又如何被统一处理？

**参考答案：**

相机侧的边界是 `Surface`：RTE 通过 `HJOGRenderWindowBridge` 创建 `OH_NativeImage` 和 OES 纹理，并把 `SurfaceId` 交给相机；相机只负责向 Surface 写入画面，RTE 调用 `OH_NativeImage_UpdateSurfaceImage()` 更新并取得最新的 OES 纹理。图片侧的边界是图片路径：`HJRteComSourceImage` 负责读取图片，并将其上传为静态的 2D 纹理。

## 第 13 题

**问题：** HJMedia 是如何实现视频超分的？超分会增加 GPU、CPU 和内存开销，项目中采用了哪些方式控制这些额外开销？

**参考答案：**

HJMedia 提供了两类超分实现。实时渲染链主要使用 `HJRteComDrawSRFilter`：输入的 2D 纹理先经过 EASU Shader 做边缘自适应放大，写入中间 FBO；再经过 RCAS Shader 做对比度自适应锐化，输出新的 2D 纹理；如果开启 `enableExtraSharpen`，还会增加一次额外锐化。整个过程是 `2D 纹理 → EASU FBO → RCAS → 可选额外锐化 → 输出 FBO`，不需要把图像读回 CPU。项目还提供 `HJBaseVideoSR` 模型超分体系，可以根据平台选择 NCNN RealESRGAN、RealCUGAN、PlainUSR、HarmonyOS MindSpore、iOS CoreML 或 VTFrameProcessor；`HJRteComDrawSRFilter` 则是更适合实时预览和推流的轻量纹理方案。

项目主要通过以下方式控制性能开销：

1. **按需启用和直接旁路**：RTE 配置中的超分节点可以关闭，关闭后 Graph 直接传递上游纹理，不执行超分；Harmony 的配置构造器默认也不会在未指定 `isEnableEnhance` 时开启增强链。
2. **限制实际处理分辨率**：`HJRteComDrawSRFilter` 优先根据已启用目标节点的画布、viewport 和渲染模式计算真正需要的输出尺寸，避免固定倍数盲目放大；找不到目标尺寸时才使用动态倍率，输入短边达到 1080 时为 1 倍、达到 720 时为 2 倍、更低时为 4 倍。倍率也可以通过参数调整。
3. **减少数据搬运和重复分配**：纹理超分始终在 GPU 的纹理和 FBO 之间流转，Shader 在 `init` 时创建后重复使用；EASU、RCAS 中间 FBO 在尺寸不变时直接复用，Graph 的输出 FBO 也通过池化机制复用。关闭额外锐化后，每帧只执行 EASU 和 RCAS 两个 pass，不执行第三个锐化 pass。
4. **优化较重的模型超分**：NCNN 后端可以使用 Vulkan GPU、FP16、Winograd、内存池和可配置线程数；`HJVideoSRWrapper` 可以把推理放到工作线程，并通过 `asyncClear` 清除同 ID 的旧等待任务，只保留最新待处理帧，避免实时视频因超分速度不足而不断积压。正在执行的任务不会被取消。
5. **缩小模型推理区域**：`HJFaceSRWrapper` 支持先检测并裁剪人脸，只对人脸 ROI 做超分，再把带位置和 Alpha 信息的结果交给后续合成；它也支持在推理前缩放输入尺寸，从而避免每帧都对整幅高分辨率画面运行重模型。

因此，实时场景优先使用 GPU 纹理超分并控制输出尺寸，质量要求更高时再选择模型超分或人脸局部超分。需要注意的是，当前源码提供了开关、倍率和后端选择等能力，但没有看到根据温度、GPU 耗时或实时帧率自动降级的完整策略；这部分仍需要上层结合设备能力和耗时统计决定是否关闭超分、降低倍率或切换轻量方案。

## 第 14 题

**问题：** HJMedia 中的人脸检测主要服务于哪些业务功能？开启人脸检测后会给实时推流带来哪些性能和功耗影响，项目又采用了哪些方式控制这些开销？

**参考答案：**

严格来说，人脸检测模型不属于 RTE 的主图像处理链，TNN、NCNN、Vision/CoreML 等检测实现在 `src/detect` 和 `src/entry/inference` 中；RTE 负责从相机画面分出送检数据，并在检测完成后消费返回的人脸信息。以 Harmony 相机链路为例，数据先按 `相机 OES 纹理 → FilterCopyOES → 2D 纹理` 流动，再从 `video2D` 分出一路到默认关闭的 `TargetPBODetect`。开启检测取帧后，该目标通过 PBO 把图像读回 CPU，交给上层推理；检测得到的“是否有人脸、脸框和关键点”再通过 `HJRteGraphProc::setFaceInfo()` 回送给 RTE。

萌颜特效确实是叠加在相机输入流上的，而不是把相机纹理送进人脸模型后由模型输出新画面。`HJRteComSourceFaceu` 根据返回的眼睛、鼻子、嘴部等关键点，让 `HJFaceuInfo` 计算贴纸的位置、旋转和缩放，并生成独立的 2D 特效纹理；RTE 配置将相机处理后的纹理和 Faceu 纹理同时连接到 UI、编码目标，目标节点依次绘制这两层，得到“相机画面 + 萌颜贴纸”的最终画面。除此之外，检测结果还用于人脸保护：没有检测到人脸时打开模糊效果；也可以给 `HJFaceAcquireWrapper/HJFaceSRWrapper` 提供人脸 ROI，只增强人脸区域。这里的人脸检测不是身份识别。

它的主要开销包括取帧、预处理、模型推理和结果消费：如果从 RTE 纹理链取帧，需要经过 FBO 和 PBO 将 GPU 图像读回 CPU；随后还要使用 libyuv 缩放并把 NV12 等格式转换成检测器需要的 RGB，再由 TNN、NCNN、Vision/CoreML 等后端执行人脸框和关键点推理，最后还会进行坐标映射、平滑以及贴纸合成。这些操作会增加 CPU/GPU 占用和内存带宽，持续逐帧运行还会提高功耗和发热；如果检测也使用 GPU，还可能与渲染、萌颜和超分争抢 GPU 时间。检测到的人脸越多，逐脸后处理和贴纸绘制开销也会相应增加。

项目通过几种方式控制开销：检测入口默认关闭并按需打开；检测前会把输入缩放到较小的模型尺寸，NCNN RetinaFace/SCRFD 常用约 320 像素级输入，并支持选择推理后端、GPU 和线程数；异步检测使用 `asyncClear` 清除同一任务 ID 的旧等待帧，只保留较新的待处理帧，避免推理速度跟不上时队列不断积压；纹理读回使用双 PBO 交替提交和映射上一帧，预处理缓冲区也会复用，减少同步等待和重复分配。需要注意的是，双 PBO 不能消除 GPU 到 CPU 的数据搬运，`asyncClear` 也不是固定频率跳帧；当前源码中没有看到完整的温控或按帧率自动降频策略，上层仍应在不需要萌颜、人脸保护或人脸超分时关闭检测，并根据设备性能控制调用频率。

## 第 15 题

**问题：** 人脸检测是在 RTE 图像处理链中完成的吗？萌颜特效是如何叠加到相机输入流上的？

**参考答案：**

人脸检测模型不是 RTE 主图像处理链中的滤镜节点。以 Harmony 相机链路为例，相机输出的 OES 纹理先经过 `FilterCopyOES` 转为 2D 纹理；`video2D` 再分出一条送检支路：`2D 纹理 → TargetPBODetect → PBO 读回 CPU → 上层人脸检测 → HJRteGraphProc::setFaceInfo()`。因此，RTE 负责提供送检画面并接收检测结果，真正的 TNN、NCNN 等模型推理位于 `src/detect` 和 `src/entry/inference`。

## 第 16 题

**问题：** 结合 HJMedia 项目，介绍一下 H.264、H.265、RTMP、AAC、PCM、YUV、RGB 等音视频相关概念，以及它们在推流链路中的关系。

**参考答案：**

这些概念属于不同层次：YUV、RGB 和 PCM 是未压缩的原始数据；H.264、H.265 和 AAC 是压缩编码格式；RTMP 是传输编码后音视频的网络协议。HJMedia 也在 `HJDataType` 中将数据分为 `HJDATA_TYPE_RS`，即 YUV、PCM 等原始流，以及 `HJDATA_TYPE_ES`，即 AVC、HEVC、AAC 等编码流。

视频链路可以概括为：`相机 OES 纹理 → RTE 2D/RGBA 纹理 → 编码器 Surface（NV12 配置）→ H.264/H.265 → FLV Video Tag`。RGB 使用红、绿、蓝表示像素，RGBA 还包含透明度，适合图片、OpenGL 渲染和 AI 处理，但占用的内存和带宽较大；HJMedia 的图片纹理、RTE FBO 和 PBO 读回主要使用 RGB/RGBA。YUV 将亮度 Y 与色度 U、V 分开，便于对色度降采样，常见的 I420 是 Y、U、V 三个平面，NV12 是 Y 平面加交错 UV 平面；8 位 YUV420 平均每像素约 1.5 字节，更适合相机和编解码器。项目通过 `HJVideoConverter`、`HJTransferMediaData` 和 libyuv 在 I420、NV12、RGB、RGBA 之间转换，Harmony 视频编码器配置的像素格式为 `AV_PIXEL_FORMAT_NV12`。

H.264 又叫 AVC，H.265 又叫 HEVC，它们都通过帧内预测、帧间预测、变换、量化和熵编码压缩原始视频。H.264 码流由 NALU 组成，常见的有 SPS、PPS、IDR 和 SEI；H.265 还增加了 VPS。H.265 通常能以更低码率获得接近 H.264 的画质，但编解码复杂度和兼容成本更高。项目通过 `HJPusherVideoInfo::videoCodecId` 选择 H.264 或 H.265，`HJVEncOHCodec` 分别使用 `video/avc` 和 `video/hevc` 创建 Harmony 硬件编码器，并根据分辨率、帧率、码率和 GOP 配置编码。

Annex B 和 AVCC 不是两种编码，而是 H.264/H.265 NALU 的两种组织方式：Annex B 使用 `00 00 01` 或 `00 00 00 01` 起始码分隔 NALU，AVCC 使用四字节长度前缀。`HJESParser::proc_avc_data()` 和 `proc_hevc_data()` 会检查编码帧是否带有起始码：如果是 Annex B，就去掉起始码并为每个 NALU 写入四字节长度；如果已经是长度前缀格式，就直接使用。同时，SPS/PPS 或 VPS/SPS/PPS 会被整理成 `avcC/hvcC` 配置记录，作为 RTMP 视频序列头。

音频链路可以概括为：`麦克风 PCM → 重采样/FIFO → AAC → FLV Audio Tag`。PCM 是未经压缩的音频采样，必须同时说明采样率、声道数、S16/Float 等采样格式以及平面或交错布局。`HJPluginAudioResampler` 负责统一这些参数，FIFO 再将 PCM 整理成编码器需要的固定帧大小。HJMedia 使用 FDK-AAC 将 PCM 编码为 AAC-LC，每帧按 1024 个采样组织；编码器生成的 `AudioSpecificConfig` 被保存为 AAC 配置头。写入 FLV 时，`HJFLVUtils` 先发送 AAC Sequence Header，普通 AAC 数据帧如果带有 ADTS 头，则先去掉 ADTS 再写入 Audio Tag。

RTMP 本身不压缩音视频，它负责建立推流连接并发送音视频消息。在 `HJGraphPusher` 中，视频编码器输出 H.264/H.265，音频编码器输出 AAC，`HJPluginAVInterleave` 比较两路 DTS 并按时间顺序交织，`HJRTMPMuxer` 再构造 FLV Audio/Video Tag，最后由 `HJRTMPWrapper` 通过 librtmp 完成 `RTMP_SetupURL`、连接和 `RTMP_Write`。项目还支持 Enhanced RTMP，用扩展 VideoTag 和 FourCC 承载 HEVC 等编码。因此整体关系就是：RGB/YUV 和 PCM 是被处理的原始数据，H.264/H.265 和 AAC 负责压缩，FLV Tag 负责组织音视频与时间戳，RTMP 负责把这些数据发送到直播服务器。

## 第 17 题

**问题：** HJMedia 项目使用了 FFmpeg 的哪些功能？这些功能主要位于音视频链路的哪些环节？

**参考答案：**

FFmpeg 在 HJMedia 中主要作为通用媒体底座使用，而不是包办整条推流链路，具体分为以下几个环节：

1. **媒体数据与时间戳表示**：`HJMediaFrame` 使用 FFmpeg 的 `AVPacket` 表示 H.264、H.265、AAC 等压缩帧，使用 `AVFrame` 表示解码后的 YUV、PCM；`HJMediaInfo` 使用 `AVCodecParameters`、像素格式、采样格式和声道布局保存流信息，并用 `av_rescale_q()`、`av_packet_rescale_ts()` 转换时间基。这些结构贯穿解封装、编解码、转换和封装流程。
2. **解封装**：`HJFFDemuxer` 通过 libavformat 的 `avformat_open_input()`、`avformat_find_stream_info()`、`av_read_frame()` 和 `avformat_seek_file()` 打开媒体 URL、识别音视频轨、读取压缩包并完成 Seek；`HJPluginFFDemuxer` 被直播播放器、点播播放器和音乐播放器使用。数据变化是：`文件或网络媒体 → AVPacket 压缩帧`。
3. **编解码**：`HJVDecFFMpeg` 和 `HJADecFFMpeg` 使用 libavcodec 将压缩视频、音频解码为 YUV 和 PCM，是播放器的软件解码后端；`HJVEncFFMpeg` 和 `HJAEncFFMpeg` 也提供通用的软件或 FFmpeg 硬件编码能力，用于框架的编码节点。数据变化是：解码时 `H.264/H.265/AAC AVPacket → YUV/PCM AVFrame`，编码时方向相反。
4. **格式转换与音频整理**：`HJAudioConverter` 使用 libswresample 统一 PCM 的采样率、采样格式和声道布局，`HJAudioFifo` 使用 `AVAudioFifo` 将 PCM 整理成固定采样数；`HJVideoConverter` 使用 libswscale 完成像素格式、尺寸转换，同时部分 I420、RGBA 转换和旋转由 libyuv 完成。该环节通常位于解码后到渲染前，或采集后到编码前。
5. **码流解析与格式适配**：`HJBSFParser`、`HJH2645Parser` 使用 FFmpeg Bitstream Filter 和 H.264/H.265 解析能力，处理 `h264_mp4toannexb`、`hevc_mp4toannexb`，并解析 SPS、PPS、VPS、extradata 和 NALU 长度信息，供解码、封装及码流参数识别使用。需要注意，推 RTMP 时的反向适配——把 Annex B NALU 改为长度前缀并生成 `avcC/hvcC`——主要由项目自己的 `HJESParser` 完成。
6. **封装与本地录制**：`HJFFMuxer` 使用 libavformat 创建输出容器和音视频流，通过 `avformat_write_header()`、`av_interleaved_write_frame()`、`av_write_trailer()` 写入文件或其他 FFmpeg 输出；在 `HJGraphPusher::openRecorder()` 中，编码后的音视频经过交织后连接到 `HJPluginFFMuxer`，用于本地录制。数据变化是：`H.264/H.265/AAC AVPacket → MP4 等封装文件`。

因此，播放主链可以概括为：`媒体 URL → FFmpeg 解封装 → H.264/H.265/AAC AVPacket → FFmpeg 软件解码或平台硬解 → YUV/PCM → 转换 → 渲染`；录制链是：`编码帧 → 交织 → FFmpeg 封装 → 本地文件`。Harmony 推流主链需要单独区分：视频编码使用 `HJPluginVideoOHEncoder`/OH Codec，音频编码使用 `HJPluginFDKAACEncoder`，RTMP 侧由 `HJRTMPMuxer` 构造 FLV Tag、`HJRTMPWrapper` 调用 librtmp 发送，因此“Harmony 推流编码和 RTMP 网络发送”并不是由 FFmpeg 完成的；FFmpeg 在这条链上更多承担数据结构、时间基、格式转换和可选码流解析等基础能力。
