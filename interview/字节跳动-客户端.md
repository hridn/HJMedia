4. 云端文档转码平台的整体架构如何设计？
答案：
上传服务负责创建上传会话、签发分片上传凭证并记录文件元数据。客户端把分片直接上传到对象存储，完成后由服务端校验分片清单和文件摘要，再创建转码任务。任务进入消息队列，由不同格式的转码工作节点消费。
转码任务应使用明确的状态机：
CREATED -> UPLOADING -> UPLOADED -> QUEUED
        -> RUNNING -> SUCCEEDED
                   -> RETRY_WAIT -> RUNNING
                   -> FAILED

状态转换必须带条件更新。例如工作节点只能把 QUEUED 改为 RUNNING，不能无条件覆盖状态。每次重试还要带执行代数 generation，防止上一次超时任务晚到的成功结果覆盖新任务。
原文件、临时产物和最终预览文件应使用不同存储前缀，并设置不同生命周期策略。转码节点运行第三方解析器时，需要使用容器、资源限制和沙箱隔离，避免恶意文档触发任意代码执行或资源耗尽。
5. MySQL 与 Redis 出现数据不一致时，为什么“先更新数据库，再删除缓存”仍然不是绝对安全的？
答案：
该方案能覆盖大部分场景，但仍存在竞态。假设读请求先查询数据库得到旧值，随后写请求更新数据库并删除缓存，最后读请求把先前查到的旧值写回缓存，此时缓存仍会被污染。
工程上可以根据一致性要求组合使用以下方案：缓存设置合理过期时间；更新后延迟二次删除；缓存写入携带数据版本号；热点 key 使用互斥重建；通过数据库变更日志异步修正缓存。
更稳妥的方式是让缓存中的值带数据库版本：
cache_key -> {
    version: 108,
    value: ...
}

缓存更新脚本只接受不小于当前版本的新值：
local old = redis.call('HGET', KEYS[1], 'version')
if old and tonumber(old) > tonumber(ARGV[1]) then
    return 0
end

redis.call('HSET', KEYS[1],
    'version', ARGV[1],
    'value', ARGV[2])
redis.call('EXPIRE', KEYS[1], ARGV[3])
return 1

这样即使较旧的更新事件晚到，也不能覆盖较新的缓存内容。
6. 基于 Binlog 同步缓存时，如何处理乱序、重复、回放和表结构变更？
答案：
Binlog 消费者应记录位点，例如 GTID 或文件位置，并把位点推进与业务处理绑定起来。消息可能因消费者重启而重复投递，因此同步逻辑必须幂等，不能假设每条变更只执行一次。
单分区可以维持局部顺序，但多个分区之间通常没有全局顺序。应使用主键作为分区键，使同一行的更新进入同一分区；缓存中保存行版本、更新时间或业务序列号，拒绝旧事件覆盖新值。
事务型 Binlog 还要考虑同一事务内多行修改的原子可见性。如果下游不能原子应用整个事务，短时间内可能观察到中间状态。对于强关联数据，可以把事务 ID 和提交标识一起传递，下游收齐后再应用。
表结构变更不能直接忽略。消费者需要识别 schema 版本，并兼容新增列、默认值及字段类型升级；删除或重命名字段时，应先让所有消费者完成兼容，再执行数据库 DDL。
7. 如何设计一个不会被击穿的多级缓存？
答案：
多级缓存可以由进程内缓存和 Redis 组成。进程内缓存降低 Redis 压力，但会引入多个实例之间的数据过期差异，因此更适合保存短 TTL 数据，或者通过广播事件主动失效。
热点 key 失效时不能让所有请求同时访问数据库。可以对单个 key 使用请求合并，只允许一个请求负责重建，其余请求等待结果。对允许短暂旧数据的场景，还可以使用逻辑过期：缓存数据过期后先返回旧值，由后台线程异步刷新。
物理过期时间 = 30 分钟
逻辑过期时间 = 5 分钟

还应给 TTL 增加随机抖动，避免大量 key 同时失效。不存在的数据可以缓存较短时间的空值；如果恶意请求会构造海量不存在的 key，则需要布隆过滤器或入口限流。
8. RabbitMQ 出现重复消费和消息丢失时，应该分别从哪些位置排查？
答案：
生产者、Broker 和消费者三个阶段都可能出问题。生产者发送后网络中断，无法判断 Broker 是否收到，重试就可能产生重复消息；Broker 如果未开启持久化或消息尚未落盘就故障，可能丢失消息；消费者处理完成但确认消息前崩溃，也会造成重新投递。
生产端应使用 publisher confirms，并为消息设置稳定的业务 ID。交换机、队列和消息都要按持久化要求配置。消费者必须在业务处理完成后手动确认，而不是收到消息后立即确认。
幂等不能只依靠内存集合，可以使用数据库唯一约束：
CREATE TABLE consumed_message (
    consumer_name VARCHAR(64) NOT NULL,
    message_id    VARCHAR(128) NOT NULL,
    consumed_at   DATETIME NOT NULL,
    PRIMARY KEY (consumer_name, message_id)
);

消费者在同一数据库事务中插入消费记录并修改业务数据。若唯一键冲突，说明该消息已经成功处理，可以直接确认。
9. RabbitMQ 的消息确认成功，但业务事务回滚了，如何处理？
答案：
如果在业务事务提交前发送 ACK，事务随后回滚，消息就会永久丢失；如果事务提交成功后 ACK，但 ACK 在网络中丢失，Broker 会重新投递。因此正确顺序通常是先提交业务事务，再确认消息，并通过幂等处理重复投递。
如果消费逻辑还需要发布下一条消息，则会出现数据库提交与消息发送的双写问题。可在业务事务中同时写入 Outbox 表，由独立发布器扫描 Outbox 并发送消息。发布成功后更新投递状态，即使发布器崩溃，也只会导致重复发送，不会永久漏发。
BEGIN;

UPDATE convert_task
SET status = 'SUCCEEDED'
WHERE task_id = ? AND status = 'RUNNING';

INSERT INTO message_outbox(event_id, topic, payload, status)
VALUES (?, 'convert.finished', ?, 'NEW');

COMMIT;

下游仍需按 event_id 幂等消费，因为 Outbox 发布器可能在发送成功但更新状态前崩溃。
10. 如何设计消息队列的重试、死信和退避机制，避免故障期间把服务打死？
答案：
消费失败后立即重新入队会形成高速失败循环，不仅占满 CPU 和网络，还会阻塞正常消息。应按照异常类型决定是否重试：参数错误、权限错误等永久性异常直接进入死信队列；网络超时、依赖服务暂时不可用等异常才进入延迟重试。
可以设置多级重试队列：
原队列
  -> 10 秒重试队列
  -> 1 分钟重试队列
  -> 10 分钟重试队列
  -> 死信队列

每条消息记录重试次数、首次失败时间和最近错误摘要。达到次数或总时长上限后进入死信队列，由人工或补偿任务处理。重试消息最好保留原业务 ID，避免每次重试生成新 ID 破坏幂等判断。
如果依赖服务整体不可用，还应配合熔断和消费降速，而不是让所有消息继续失败重试。
11. 大文件分片上传如何实现断点续传、秒传和完整性校验？
答案：
客户端先请求创建上传会话，服务端返回 upload_id、推荐分片大小和已上传分片列表。每个分片应带分片编号、长度和摘要。服务端或对象存储确认分片成功后，记录对应 ETag。
客户端恢复上传时只补传缺失分片。完成上传不能只检查分片数量，还要检查编号是否连续、大小是否合法，并根据分片摘要或最终文件摘要校验内容完整性。
秒传不能只根据文件名和大小判断，应使用内容摘要，但直接相信客户端提供的摘要也不安全。服务端需要确认当前用户有权引用已存在对象，并在必要时抽样或完整校验。
struct PartMeta {
    uint32_t index;
    uint64_t size;
    std::string sha256;
    std::string etag;
};

bool IsComplete(std::vector<PartMeta> parts, uint32_t expectedCount) {
    if (parts.size() != expectedCount) return false;

    std::sort(parts.begin(), parts.end(),
              [](const auto& a, const auto& b) {
                  return a.index < b.index;
              });

    for (uint32_t i = 0; i < expectedCount; ++i) {
        if (parts[i].index != i || parts[i].size == 0)
            return false;
    }
    return true;
}

12. 上传接口返回成功，但文件最终不可用，如何设计状态和补偿流程？
答案：
接口成功需要区分“分片已接收”和“文件已提交”。所有分片上传完成后，还要执行合并、摘要校验、病毒扫描、格式识别和对象存储确认，因此不能过早返回最终成功。
可以把文件状态设计为：
UPLOADING -> ASSEMBLING -> VERIFYING -> AVAILABLE
                       \-> CORRUPTED
                       \-> FAILED

提交操作需要幂等。同一个 upload_id 重复提交时，如果正在处理就返回当前状态，如果已经完成就返回文件 ID，不能重复创建文件记录。
后台扫描长时间停留在中间状态的上传会话，查询对象存储实际状态后进行推进或回滚。临时分片不能立即删除，应设置生命周期规则，在保留足够排障时间后自动清理。
13. unique_ptr、shared_ptr 和裸指针在接口设计中分别表达什么所有权？
答案：
unique_ptr<T> 表示独占所有权，适合工厂返回值以及明确转移生命周期的接口。shared_ptr<T> 表示共享所有权，只有对象确实由多个独立模块共同延长生命周期时才应该使用。裸指针和引用通常表达非拥有访问，即调用者保证被访问对象仍然存活。
std::unique_ptr<Parser> CreateParser(Format format);

void RegisterObserver(Observer* observer);  // 非拥有
void ReplaceEngine(std::unique_ptr<Engine> engine); // 转移所有权
void Submit(std::shared_ptr<const Task> task); // 共享只读任务

不能为了“避免悬空”而无差别使用 shared_ptr。它会隐藏生命周期边界，还可能形成循环引用。若两个对象相互关联，应让一个方向拥有对象，另一个方向使用裸指针、引用或 weak_ptr。
14. 移动语义中，为什么 std::move 并不会真的移动对象？
答案：
std::move 本质上只是把表达式转换为右值引用，从而允许编译器选择移动构造或移动赋值。真正的资源转移发生在目标类型的移动函数内部。如果类型没有移动构造函数，或者源对象是 const，最终仍可能调用复制构造函数。
class Buffer {
public:
    Buffer(size_t n) : data_(new char[n]), size_(n) {}

    Buffer(Buffer&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),
          size_(std::exchange(other.size_, 0)) {}

    Buffer& operator=(Buffer&& other) noexcept {
        if (this == &other) return *this;
        delete[] data_;
        data_ = std::exchange(other.data_, nullptr);
        size_ = std::exchange(other.size_, 0);
        return *this;
    }

    ~Buffer() { delete[] data_; }

private:
    char* data_;
    size_t size_;
};

移动构造通常应标记 noexcept。例如 std::vector 扩容时，为保证异常安全，如果元素移动构造可能抛异常，容器可能改用复制构造。
15. C++ 对象析构期间抛出异常会发生什么？
答案：
如果析构函数在正常路径中抛出异常，调用者理论上可以捕获；但如果程序正在进行异常栈展开，此时另一个析构函数再次抛出异常，运行时会调用 std::terminate。
因此析构函数通常必须满足不抛异常的约束。资源释放失败时可以记录日志、设置错误状态，或者提供显式的 Close()、Commit() 方法，让调用者在进入析构阶段前处理错误。
class Transaction {
public:
    void Commit() {
        databaseCommit();   // 允许向调用者报告异常
        committed_ = true;
    }

    ~Transaction() noexcept {
        if (!committed_) {
            try {
                databaseRollback();
            } catch (...) {
                LogCurrentException();
            }
        }
    }

private:
    bool committed_ = false;
};

不能把关键业务动作完全依赖析构函数，例如文件落盘、事务提交等，因为析构函数缺少可靠的错误返回通道。

1. 请做一下自我介绍
2. HTTP/2 相比 HTTPS 分别解决了什么问题？HTTP/2 是否必须运行在 TLS 上？
答案：
HTTPS 本质上是 HTTP 运行在 TLS 之上，解决的是机密性、完整性和身份认证问题；HTTP/2 是应用层协议版本，主要改善 HTTP/1.1 的传输效率，包括二进制分帧、单连接多路复用、头部压缩和流优先级。
HTTP/2 规范本身并未强制 TLS，明文形式称为 h2c，但主流浏览器基本只支持基于 TLS 的 h2。TLS 握手期间，客户端和服务端通过 ALPN 协商最终使用 h2 还是 http/1.1。
HTTP/2 消除了 HTTP/1.1 的应用层队头阻塞，但多个流仍共享同一条 TCP 连接。一旦底层 TCP 丢包，后续已经到达的字节也不能越过缺失序列号交付，因此所有流都会受到影响。HTTP/3 改用 QUIC，使不同流拥有独立的可靠传输状态，才进一步缓解了传输层队头阻塞。
3. TLS 1.3 完整握手中，客户端如何确认自己连接的不是中间人？
答案：
客户端会验证服务端发送的证书链能否追溯到本地信任的根 CA，同时检查证书有效期、用途、吊销状态以及域名是否与 SAN 匹配。仅验证证书还不够，服务端还会使用证书对应的私钥对握手 transcript 进行签名，客户端通过证书中的公钥验证签名，从而证明对方确实持有私钥。
TLS 1.3 使用临时 Diffie-Hellman 参数生成共享密钥，私钥不会直接在网络上传输。之后双方通过 HKDF 从共享秘密和握手 transcript 派生握手密钥及应用数据密钥。Finished 消息又对前序握手内容做认证，任何握手字段被篡改都会导致校验失败。
0-RTT 数据不具备完整的抗重放能力，因此只能用于天然幂等的操作，不能直接承载扣款、创建订单等请求。
4. RSA、ECDHE、AES-GCM 和 ChaCha20-Poly1305 在现代 TLS 中分别承担什么职责？
答案：
RSA 在现代 TLS 中主要用于证书签名和身份认证，TLS 1.3 已经移除了 RSA 密钥交换。ECDHE 用于协商一次性的共享秘密，提供前向安全性：即使服务端长期私钥未来泄露，历史会话也不能被直接解密。
AES-GCM 和 ChaCha20-Poly1305 都属于 AEAD 算法，同时提供加密和完整性认证。AES-GCM 在支持 AES-NI 的桌面端和服务器上通常性能很好；ChaCha20-Poly1305 对专用硬件依赖较少，在部分移动设备上更有优势。
AEAD 的 nonce 不能在同一密钥下重复。工程实现中通常由固定 IV 与单调递增的记录序号组合生成，而不能简单地每次随机生成后假设永不冲突。
5. TCP 数据流中没有消息边界，客户端如何正确处理拆包、粘包和恶意长度字段？
答案：
可以使用固定长度头部描述消息类型、版本、负载长度和校验信息。读取时先累积到完整头部，再解析负载长度；只有缓冲区包含完整帧时才交给上层。必须对长度设置硬上限，并在计算总长度时防止整数溢出，否则攻击者可以构造超大长度造成内存耗尽或越界。
struct FrameHeader {
    uint32_t magic;
    uint16_t version;
    uint16_t type;
    uint32_t body_len;
};

constexpr uint32_t kMagic = 0x544C4D31;
constexpr size_t kMaxBody = 4 * 1024 * 1024;

std::optional<std::string> TryDecode(std::string& buffer) {
    if (buffer.size() < sizeof(FrameHeader)) return std::nullopt;

    FrameHeader net{};
    std::memcpy(&net, buffer.data(), sizeof(net));
    const uint32_t magic = ntohl(net.magic);
    const uint32_t bodyLen = ntohl(net.body_len);

    if (magic != kMagic || bodyLen > kMaxBody)
        throw std::runtime_error("invalid frame");

    if (bodyLen > SIZE_MAX - sizeof(FrameHeader))
        throw std::overflow_error("frame length overflow");

    const size_t frameLen = sizeof(FrameHeader) + bodyLen;
    if (buffer.size() < frameLen) return std::nullopt;

    std::string body(buffer.data() + sizeof(FrameHeader), bodyLen);
    buffer.erase(0, frameLen);
    return body;
}

真实项目中不宜频繁调用 erase(0, n) 搬移内存，可以使用读写游标、环形缓冲区或分段 buffer。
6. 客户端与服务端对同一条 Protobuf 消息解析结果不一致，如何设计抓包和定位工具？
答案：
定位工具不能只打印原始十六进制数据，还应完整保存方向、连接标识、单调时钟时间戳、协议版本、帧头、原始 payload 和 schema 版本。首先在 TLS 加密前、业务反序列化前后分别埋点，以确定差异来自传输、解密、分帧还是反序列化。
解析端要支持加载对应版本的 descriptor set，通过反射解析消息，保留未知字段，并同时展示字段编号、wire type、原始字节和解释后的值。若客户端和服务端 schema 不一致，应检查是否复用了旧字段编号、是否修改了字段类型、是否错误处理 oneof，以及不同语言对整数有符号性和默认值的处理是否一致。
敏感字段不能直接落盘。可按字段号配置脱敏，对 token、手机号等内容做删除或不可逆摘要；抓包文件还应设置大小上限、滚动策略和访问权限。
7. Protobuf 和 JSON 在兼容性、性能及可观测性上有什么本质差异？
答案：
Protobuf 使用字段编号和 wire type 表示数据，编码紧凑、解析速度快，并支持未知字段透传，适合强约束、高吞吐的内部 RPC 和长连接协议。JSON 自描述性更好，可直接阅读和调试，适合开放接口、配置和对兼容性要求较宽松的场景，但体积和解析成本一般更高。
Protobuf 的兼容性依赖严格的 schema 演进纪律：已删除字段的编号和名称应放入 reserved，不能随意更改字段编号，也不能假设新增字段一定被旧客户端识别。optional、默认值以及字段缺失是三个容易混淆的概念。
JSON 的问题不只是性能。大整数经过 JavaScript 时可能超过安全整数范围；重复 key 的处理没有统一结果；数字、空值和字段缺失也可能在不同实现间产生语义偏差。因此外部 JSON 接口同样需要明确 schema。
8. DNS 解析完成后，到一条 HTTPS 请求真正发出，中间经历了哪些关键步骤？
答案：
客户端会先检查浏览器或应用缓存、系统缓存及 hosts，未命中时由 stub resolver 请求递归 DNS 服务器。递归服务器可能依次查询根、顶级域和权威服务器，最终返回 A、AAAA 或 CNAME 等记录。客户端选定目标 IP 后，根据路由表确定下一跳；若目标不在同一网段，需要通过 ARP 或 NDP 获取网关链路层地址。
随后通常进行 TCP 三次握手，再进行 TLS 握手；TLS 中会完成版本与密码套件协商、证书验证、密钥派生和 ALPN 协商。连接建立后，应用才会发送 HTTP 请求。数据经过 HTTP、TLS、TCP、IP 和链路层逐层封装，由中间路由器转发，服务端按相反顺序解封装。
实际实现还可能涉及代理、NAT、Happy Eyeballs、连接池复用、会话恢复和 0-RTT，所以并非每次请求都完整重复全部步骤。
9. epoll 的边缘触发模式为什么必须循环读到 EAGAIN？如何避免事件丢失？
答案：
边缘触发只在文件描述符状态发生变化时通知。如果收到一次可读通知后只读取部分数据，套接字仍处于可读状态，但未必再次产生新的边缘，因此剩余数据可能长期留在接收缓冲区。
套接字必须设为非阻塞，并持续调用 read，直到返回 -1 且 errno == EAGAIN/EWOULDBLOCK。EINTR 应重试，返回 0 表示对端完成有序关闭，其他错误则关闭连接。
void DrainRead(int fd, Buffer& buf) {
    char tmp[8192];
    for (;;) {
        ssize_t n = ::read(fd, tmp, sizeof(tmp));
        if (n > 0) {
            buf.append(tmp, static_cast<size_t>(n));
        } else if (n == 0) {
            CloseConnection(fd);
            return;
        } else if (errno == EINTR) {
            continue;
        } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
            break;
        } else {
            CloseConnection(fd);
            return;
        }
    }
    DecodeFrames(buf);
}

多线程处理同一 epoll 实例时，还要考虑惊群、fd 复用和对象生命周期问题。不能仅凭 fd 查找连接后长期持有裸指针，因为旧连接关闭后相同 fd 可能已被新连接复用。
