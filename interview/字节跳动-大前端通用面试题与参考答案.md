## 第一部分：原 18 题与参考答案

### 1、说下 SSE 和 Websocket？

**参考回答：**

SSE（Server-Sent Events）和 WebSocket 都能建立长连接，但通信模型不同：

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端到客户端单向推送 | 客户端与服务端全双工 |
| 基础协议 | 普通 HTTP，响应类型通常为 `text/event-stream` | 先通过 HTTP Upgrade 握手，再进入 WebSocket 协议 |
| 数据类型 | 以 UTF-8 文本事件为主 | 文本与二进制都支持 |
| 重连 | 协议包含事件 ID、重试间隔等机制，客户端实现通常较简单 | 需要业务自行设计心跳、重连、补消息和去重 |
| 基础设施 | 更容易复用 HTTP 鉴权、网关和代理 | 代理、网关和连接管理需要专门支持 |
| 典型场景 | AI 文本流、通知、进度推送 | 聊天、弹幕、PK、连麦信令、实时双向控制 |

选择时不能只说“SSE 简单、WebSocket 强大”，而要看方向、频率、二进制需求和恢复语义。AI 对话通常主要由服务端持续返回 token，适合 SSE；花椒直播弹幕与连麦状态需要双方主动发送，使用 WebSocket 更合理。

在 Harmony 原生应用中，不能默认存在浏览器的 `EventSource`。如果网络库支持流式响应，可以解析 `text/event-stream`；无论使用哪种 API，都要处理粘连 chunk、半条事件、页面退出后的取消以及断线续传。

### 2、Promise 和 async/await 的使用区别？

**参考回答：**

Promise 是异步结果的抽象，`async/await` 是建立在 Promise 之上的语法形式，而不是另一套异步机制。

- `async` 函数一定返回 Promise；直接 `return value` 会等价地包装为 fulfilled Promise。
- `await` 会暂停当前 async 函数的后续逻辑，但不会阻塞 UI 线程；Promise 落定后，后续代码通过微任务继续执行。
- Promise 链适合并行组合与函数式编排，例如 `all`、`allSettled`、`race`；`async/await` 更适合表达顺序流程和统一使用 `try/catch/finally`。

最常见错误是把本可并行的任务写成连续 await：

```ts
// 串行：第二个请求要等待第一个结束。
const user = await loadUser();
const config = await loadConfig();

// 并行启动，再统一等待。
const [user, config] = await Promise.all([
  loadUser(),
  loadConfig()
]);
```

`Promise.all` 任一失败会立即 reject，但其他底层任务并不会自动取消；需要结合网络库的取消能力。页面退出时也不能只是不再 await，还要取消任务或阻止晚到结果更新已销毁页面。

### 3、日常开发使用AI工具的场景与技巧？

**参考回答：**

我把 AI 放在完整研发闭环中，而不是只用于生成代码：

1. **理解代码**：建立仓库导航、调用链和术语表；关键结论回到源码、日志和官方文档验证。
2. **方案设计**：提供目标、现状与约束，让 AI 列多个方案、风险和 trade-off；最终判断由工程师完成。
3. **实现与重构**：把任务切成小改动，明确允许修改的文件、保持不变的接口和代码规范。
4. **测试与排障**：生成边界用例、最小复现和排查假设，运行构建、测试、日志和 Profiler 验证。
5. **知识沉淀**：把反复出现的流程写成 Spec、Skill、检查清单或项目文档。

实用技巧是给 AI 足够具体的上下文：目标、相关文件、版本、错误日志、限制条件、期望输出和验收命令；要求它先列假设与风险，再修改代码；最后只根据实际 diff 和验证结果判断，不根据 AI 的自我评价判断。

结合 HJMedia 可以诚实地说：镜像/贴纸功能的方案和编码由 AI 完成，我负责定义效果、提供仓库上下文、构建联调和最终验收；不会把 AI 产出包装成自己手写的 OpenGL 算法。工程师最终仍对需求、质量和发布结果负责。

### 4、谈谈你对Skill、MCP这类AI相关概念的理解？

**参考回答：**

两者解决的是不同层次的问题：

- **Skill**：面向某一类任务的可复用方法包，通常包含何时触发、执行步骤、约束、参考资料、脚本和验收方式。它回答“这类任务应该怎么做”。Skill 不是行业唯一标准，不同 Agent 产品的组织方式可能不同。
- **MCP（Model Context Protocol）**：AI 应用连接外部系统的开放协议。MCP Server 可以暴露 Resources、Tools 和 Prompts，Client 负责发现能力并按协议交互。它回答“能访问什么、以什么接口访问”。

例如“处理 GitHub Review”可以写成一个 Skill，规定先读评论、复现、修改、测试再回复；Skill 执行过程中可以通过 MCP Server 读取仓库、查询 PR 或调用工具。

MCP 只统一连接方式，不自动解决权限和结果正确性。需要最小权限、参数校验、工具白名单、写操作确认、调用审计、超时和结果大小限制；Skill 也需要版本化和回归验证，避免流程与当前代码库脱节。

### 5、数组的 map() 和 forEach() 有什么区别？

**参考回答：**

核心区别在语义和返回值：

- `map()` 表示“把每个元素映射成一个新元素”，返回一个等长的新数组。
- `forEach()` 表示“对每个元素执行副作用”，返回值始终是 `undefined`。
- 两者都会跳过稀疏数组中的空槽，都不能像普通循环一样直接 `break`。
- 两者都不会深拷贝元素。若元素是对象，回调拿到的仍是原对象引用。

```ts
const source = [{ score: 1 }, { score: 2 }];

const doubled = source.map(item => item.score * 2);
// doubled: [2, 4]，source 结构未变。

source.forEach(item => {
  item.score += 1;
});
// 修改了两个原对象内部的 score。
```

需要得到新数组时选 `map`；执行打点、注册监听等副作用时选 `forEach`。如果只是为了副作用却使用 `map`，会创建一个没有用途的新数组，语义和内存都不合适。

### 6、forEach()可以改变数组吗

**参考回答：**

可以，但要区分“修改回调参数”“修改元素对象”“通过原数组修改槽位”三种情况：

```ts
const numbers = [1, 2, 3];
numbers.forEach(item => {
  item = item * 2; // 只修改局部变量，不改变数组。
});

numbers.forEach((item, index, array) => {
  array[index] = item * 2; // 直接修改数组槽位，numbers 变为 [2, 4, 6]。
});

const users = [{ name: 'A' }];
users.forEach(user => {
  user.name = 'B'; // 修改同一个对象，原数组看到变化。
  user = { name: 'C' }; // 仅改变局部引用，原数组不受影响。
});
```

遍历过程中执行 `push`、`splice`、`shift` 等结构性修改虽然允许，但容易跳过元素或得到难以理解的结果。工程上应避免边遍历边改结构，优先生成新数组，或者先计算变更再统一应用。

### 7、鸿蒙中lazyForEach懒加载的原理

**参考回答：**

规范名称是 `LazyForEach`。它通过数据源协议和容器可视范围配合，实现子组件按需创建：

1. 数据源实现 `IDataSource`，提供总数、按索引取数据以及数据变化监听的注册/注销。
2. `List`、`Grid`、`Swiper`、`WaterFlow` 等支持懒加载的容器，根据当前可视区域和 `cachedCount` 请求需要的索引。
3. `LazyForEach` 只为可视区及缓存范围创建子组件，避免一次构建全部节点。
4. 数据发生新增、删除、移动、修改或整体刷新时，数据源必须通知监听器，框架才会做增量更新。
5. key 生成器必须稳定且唯一。key 改变意味着框架可能把它当成新节点；重复 key 会导致错误复用或刷新异常。

需要澄清三个误区：

- `LazyForEach` 负责 UI 节点按需创建，不会自动发起网络分页，数据预取仍由业务实现。
- 懒创建不等于完整的组件复用；若要降低反复创建成本，还要结合当前 ArkUI 版本支持的复用机制。
- `cachedCount` 不是越大越好。它用更多内存换取滚动时的提前准备，应结合单项复杂度、图片和设备性能实测。

### 8、泛型是什么，解决什么问题

**参考回答：**

泛型把类型作为参数，使同一套代码既能复用，又保留输入与输出之间的类型关系，避免为每种类型复制实现或退化为 `any`。

```ts
class Result<T> {
  constructor(
    public readonly data: T | undefined,
    public readonly error: string | undefined
  ) {}
}

function first<T>(items: T[]): T | undefined {
  return items.length > 0 ? items[0] : undefined;
}
```

泛型约束可以表达“类型至少具备某种能力”：

```ts
interface Identifiable {
  id: string;
}

function indexById<T extends Identifiable>(items: T[]): Map<string, T> {
  const result = new Map<string, T>();
  items.forEach(item => result.set(item.id, item));
  return result;
}
```

它解决的是编译期类型安全和复用问题，不是运行时校验。TypeScript/ArkTS 的泛型信息通常不会替你验证网络 JSON；跨 N-API、网络或持久化边界仍要做 schema/字段检查。ArkTS 对 TypeScript 动态特性的限制更严格，具体写法要以目标 SDK 编译规则为准。

### 9、SDD + TDD 开发新组件的完整流程是什么？

**参考回答：**

这里将 SDD 理解为 Spec-Driven Development，即规格驱动开发。完整流程是：

1. **明确问题**：用户场景、成功标准、非目标、平台与性能约束。
2. **编写 Spec**：组件职责、输入 Props/参数、事件、状态、错误语义、可访问性和生命周期。
3. **建立状态矩阵**：默认、加载、空、成功、错误、禁用、权限不足、重复点击、页面退出等。
4. **拆分逻辑与 UI**：先把状态机和纯逻辑做成可测试模块，再定义 UI 如何映射状态。
5. **TDD 红灯**：先写失败测试，证明当前行为缺失。测试包括纯逻辑、组件交互和关键集成路径。
6. **绿灯**：实现满足当前测试的最小代码，不顺手扩大范围。
7. **重构**：测试保持通过的前提下整理结构、命名与复用。
8. **验收**：运行构建、测试、视觉检查、性能和真机验证，并将实际决策回写 Spec。
9. **发布与回归**：版本说明、迁移说明、监控指标和回归用例同步落地。

AI 可以从 Spec 生成测试草案和实现，但人必须审核断言是否真的表达业务；不能为了让实现通过而把正确测试改错。

### 10、组件文档 Skills、MCP、llm.txt 三者的关系是什么？

**参考回答：**

三者位于不同层次，可以组成一条“发现文档—读取能力—按流程使用”的链路：

- **`llms.txt`**：网站根目录下的 Markdown 文档入口提案，用较小篇幅介绍站点并列出适合 LLM 阅读的关键文档。它主要帮助发现内容，不是权限协议，也不是所有模型都强制支持的标准。
- **MCP**：把组件文档、组件元数据、代码示例，甚至“查询某版本 API”“生成组件代码”等能力，以 Resources、Tools、Prompts 暴露给 AI 客户端。
- **Skill**：规定 AI 应如何完成“使用组件库开发页面”这类任务，例如先识别项目中实际安装的组件库版本，再读取对应文档，生成代码，最后运行类型检查、Story 和测试。

版本问题不能靠三者名字自动解决。可靠做法是：

1. `llms.txt` 链接到带版本的文档入口。
2. MCP Resource/Tool 返回明确的包名、版本、API 与废弃信息。
3. Skill 规定先读取项目 lockfile 或 manifest，以实际安装版本为准，禁止默认使用 latest。
4. 生成后执行类型检查和组件测试。

因此，`llms.txt` 提供导航，MCP 提供结构化访问，Skill 提供使用方法和质量门禁。

### 11、逻辑层与 UI 层分离的具体实现，MVVM是指什么，在鸿蒙中MVVM是如何实现的？

**参考回答：**

MVVM 分为：

- **Model**：领域数据、仓储、网络、数据库和业务实体。
- **View**：ArkUI 组件，只负责把状态渲染成界面，并把用户操作转成事件。
- **ViewModel**：持有页面状态，调用 Model/Service，处理业务编排，再向 View 暴露状态和命令。

逻辑与 UI 分离的关键不是创建三个目录，而是依赖方向清晰：View 可以依赖 ViewModel；ViewModel 不应依赖具体 UI 节点、颜色、弹窗或 `UIContext`；Model 更不应知道页面存在。

在 Harmony 中可以这样落地：

1. 把网络、数据库、播放器等封装为 Service/Repository。
2. ViewModel 暴露结构化页面状态，如 `loading/data/error`，以及 `load/retry/play` 等意图方法。
3. ArkUI 通过当前状态管理方案观察 ViewModel 或 Store 的变化，使用组件内状态与父子参数/事件完成绑定；选用 V1 或 V2 装饰器要跟随项目 SDK 与团队规范。
4. ViewModel 的纯逻辑使用单元测试；View 验证状态渲染和交互；跨层能力再做集成测试。

结合花椒项目：CDN/RTC 子组件负责具体播放和资源生命周期，`MainMediaComponent` 负责把业务播放数据转换成统一状态并选择实现，外层直播间只消费状态和事件。这是一种分层思想，但回答时也要承认播放器生命周期仍具有平台耦合，需要通过接口和适配器隔离。

### 12、Context 失效的常见场景？

**参考回答：**

这个问题有两种常见语境，面试时先向面试官确认。

**如果指 React Context：**

- Consumer 不在对应 Provider 子树内，只能得到默认值。
- Provider 与 Consumer 引用的不是同一个 Context 对象，例如依赖被重复打包。
- 直接修改 `value` 对象内部字段但引用没有改变，Provider 的值比较无法感知预期更新。
- `useMemo`、回调或派生状态依赖不完整，读到的是旧闭包中的值。
- Provider 在条件渲染、路由或 key 变化时被卸载重建，内部状态被重置。

**如果指 Harmony 的 `UIContext/AbilityContext`：**

- 页面、窗口或 UIAbility 已销毁，却仍在异步回调中使用旧 Context。
- 把某个页面的 `UIContext` 存为全局静态对象，切窗口或重建后继续复用。
- 多窗口场景拿错 UIContext，导致弹窗、路由等操作落到错误窗口。
- 非组件对象调用 UI 能力时没有从当前组件注入 Context，或 `getHostContext()` 返回空仍强行使用。
- Worker/TaskPool 线程直接使用只允许在 UI 线程或宿主生命周期内使用的 Context。

正确做法是让 Context 的持有范围不超过宿主生命周期；非 UI 类通过参数注入当前 Context；异步回调绑定取消标记；调用前检查宿主和页面是否仍有效。项目中的 `ToastUtils` 若静态保存 UIContext，就要特别防止页面/窗口切换后的陈旧引用。

### 13、介绍下鸿蒙中的worker和taskpool线程？

**参考回答：**

Worker 与 TaskPool 都用于把耗时工作移出主线程，但生命周期和调度方式不同：

| 维度 | TaskPool | Worker |
| --- | --- | --- |
| 线程管理 | 系统维护线程池，开发者提交任务 | 开发者创建并管理独立 Worker |
| 适合任务 | 独立、可拆分、执行完即结束的任务；批量并发任务 | 常驻、具有连续状态、需要频繁双向通信的任务 |
| 通信 | 任务参数与返回值；受跨线程传输规则约束 | `postMessage`/消息回调，适合持续消息循环 |
| 生命周期 | 通常不关心具体线程，由系统调度 | 需要管理创建、错误、退出和 `terminate` |
| 状态 | 不应依赖某个固定线程上的长期可变状态 | 可在 Worker 内维护线程私有状态 |

TaskPool 中可并发执行的函数需满足平台对并发函数的要求；传参不能假设与主线程共享任意普通对象。Worker 和 TaskPool 都有独立执行上下文，数据要通过拷贝、转移或 Sendable/共享机制传递，具体能力取决于 SDK 版本。

选择示例：批量图片缩放、分片 Hash、JSON 解析等独立任务适合 TaskPool；需要长期保持解码上下文或持续收发消息的任务更适合 Worker。二者都不应直接更新 ArkUI；结果应回到主线程后更新状态，并处理任务取消、页面退出和异常。

### 14、js闭包及其风险

**参考回答：**

闭包是函数与其词法作用域的组合。外层函数已经返回后，只要内部函数仍被引用，它仍能访问创建时捕获的变量。

```ts
function createCounter(): () => number {
  let count = 0;
  return () => ++count;
}
```

闭包可用于封装私有状态、回调和函数工厂，但有几类风险：

- **延长对象生命周期**：事件监听器、定时器或全局回调持有闭包，闭包又捕获页面、播放器或大数组，造成内存无法回收。
- **陈旧状态**：异步回调捕获旧值，晚到后覆盖新页面状态。
- **循环引用式业务链**：GC 能处理普通对象环，但只要根对象、监听器或 Native 回调仍可达，整个引用链都不会回收。
- **循环变量错误**：使用 `var` 时多个回调共享同一个绑定；应使用块级 `let` 或显式创建作用域。
- **`this` 误解**：箭头函数捕获词法 `this`，普通函数的 `this` 取决于调用方式。

花椒看播间内存泄漏是很好的真实例子：两个组件互相保存回调，闭包捕获组件实例，页面退出后仍然可达。修复方法是明确监听器所有权，在生命周期结束时取消订阅并将回调置空，而不是寄希望于 GC 自动识别“页面已经不用了”。

### 15、能展开讲讲Prompt优化吗？ 除了Prompt外，还有哪些参数可调整？Temperature与Top-K的区别？

**参考回答：**

Prompt 优化的本质是减少歧义和补足证据。一个工程任务至少应包含：

1. 目标与用户场景。
2. 相关架构、代码、版本和当前行为。
3. 允许修改的范围与禁止事项。
4. 输入输出、错误语义和样例。
5. 性能、安全、兼容和生命周期约束。
6. 可执行的验收命令与完成定义。

高效迭代方式是让模型先复述理解、列出假设和风险，再做小步修改；回答错误时补充日志、源码、接口文档和最小复现，不只是换一种语气重问。

除 Prompt 外，常见可控项还有：系统指令、提供的上下文、工具与权限、检索策略、结构化输出 schema、最大输出 token、停止条件、模型选择，以及采样参数。并非每个模型都开放相同参数。

- **Temperature**：对整体 logits 概率分布进行缩放。较低时分布更尖锐、输出更稳定；较高时随机性更强。
- **Top-K**：每一步只保留概率最高的 K 个候选 token，再从中采样。K 越小，候选范围越窄。
- **Top-P**：保留累计概率达到 P 的最小候选集合，是动态大小的 nucleus sampling。

编码和结构化抽取通常偏低随机性，创意任务可以适度提高。参数无法弥补错误上下文；对研发任务而言，源码、Spec、工具和测试往往比调整 Temperature 更重要。

### 16、鸿蒙中版本冲突如何解决

**参考回答：**

先判断是哪一层冲突，不能看到编译失败就直接删除缓存或 lockfile：

1. **SDK/API 冲突**：检查 DevEco Studio、HarmonyOS SDK、编译插件，以及 `compileSdkVersion`、`compatibleSdkVersion`、`targetSdkVersion` 是否匹配；调用高版本 API 时使用版本检查或兼容封装。
2. **OHPM 依赖冲突**：查看各模块的 `oh-package.json5` 与 `oh-package-lock.json5`，确认直接依赖、传递依赖和实际解析版本。优先升级/降级顶层依赖到兼容区间；必要时使用 OHPM 的 `overrides` 统一传递依赖版本，但要先验证 API/ABI 兼容。
3. **HAR/HSP 重复依赖**：检查多个模块是否重复打入同一 HAR、包名是否一致、静态共享包是否造成重复代码；可启用构建侧相关依赖校验辅助发现问题。
4. **Native 库冲突**：检查 `.so` 的 ABI、架构、C++ 运行时、重复符号和导出符号；统一版本或隔离符号，不能只让链接器“勉强通过”。

建议把 lockfile 纳入版本控制，保证本地与 CI 使用同一解析结果。`overrides` 是临时统一依赖树的工具，不是证明兼容；升级后要跑编译、单测、接口和真机回归。只有确认 lockfile 损坏或需要重新求解依赖时才重建，并审查完整差异。

### 17、从底层存储和缓存角度看，数组和链表有什么差别

**参考回答：**

传统数据结构层面：

- **数组**通常使用连续内存。随机访问可通过首地址加偏移直接定位，时间 `O(1)`；顺序遍历具有很好的空间局部性，CPU 能高效预取缓存行。中间插入删除需要移动后续元素。
- **链表**每个节点独立分配，通过指针连接。已知节点时插入删除可以 `O(1)`，但随机访问是 `O(n)`；指针本身占空间，节点可能分散在堆上，遍历会产生 pointer chasing 和更多 cache miss。

因此链表的渐进复杂度优势不等于实际一定更快。现代 CPU 上，数组连续访问常常明显优于链表；即使插入需要搬移，小规模 POD 数据也可能仍比大量堆分配快。

还要区分 JavaScript/ArkTS 的 `Array` 与 C 连续数组。JS 引擎会对紧凑数组做优化，稀疏、混合类型或频繁删除可能让内部表示退化；不能把所有底层细节简单等同于 `std::vector`。选型要结合访问模式、元素大小、插删位置和实际 Profiler，而不是只背复杂度。

### 18、说一下 Jsbridge 它的原理

**参考回答：**

JSBridge 是 Web/JavaScript 与 Native 之间的通信层，核心是“注册能力、序列化消息、分发调用、关联异步结果”。

一条典型 JS 调 Native 链路是：

1. Native 注册允许调用的方法及参数 schema。
2. JS 发送 `{ method, params, callbackId }`。
3. Bridge 通过消息通道、对象注入或平台提供的 Web 接口把消息交给 Native。
4. Native 校验来源、方法、权限与参数，在合适线程执行。
5. 完成后通过 callback ID、事件或 Promise 把序列化结果返回 JS。

Native 调 JS 则通过受控事件或执行已注册回调完成。不能把任意 JS 字符串直接拼接执行，也不能向所有页面暴露高权限 Native 能力。

关键风险包括：来源白名单、参数校验、权限、回调超时、页面销毁、线程切换、大对象拷贝、方法版本兼容和日志脱敏。对于图片或视频等大数据，应尽量传句柄、文件 URI 或共享缓冲信息，而不是频繁 JSON/Base64。

JSBridge 与 Harmony N-API 不完全相同：JSBridge 常指 ArkWeb 页面与 Native/ArkTS 宿主通信；N-API 是 ArkTS/JavaScript 运行时与 C/C++ 模块的进程内桥接。两者都要处理序列化、线程和生命周期，但所在边界不同。

## 第二部分：与原 18 题关联的发散问题与参考答案

> 本节问题不插入原题之间。每题都明确标注关联的原题编号。

### 发散 1：AI 流式对话使用 SSE 时，怎样做到断线续传、去重和取消？

**关联原题：第 1 题（SSE 与 WebSocket）**

**参考回答：**

服务端为每条事件生成递增 ID，并保存会话/生成任务 ID；客户端记录最后完整消费的事件 ID，重连时携带该游标。服务端能保留历史时返回缺失增量，不能保留时返回当前快照或明确要求重新生成。

客户端以 `{taskId, eventId}` 幂等去重，只提交完整解析后的事件；半条 SSE 消息留在字节缓冲区等待下一 chunk。用户点击停止时，先标记本地任务已取消，阻止晚到结果更新 UI，再调用服务端取消接口并关闭连接。页面退出同样要取消订阅，不能只隐藏组件。

### 发散 2：什么时候可以在循环中 `await`，什么时候应该并行？

**关联原题：第 2 题（Promise 与 async/await）**

**参考回答：**

后一个任务依赖前一个结果、必须保持顺序、服务端要求串行或需要严格限速时，可以在循环中 await。任务相互独立时可并行，但不能无上限地 `Promise.all` 数千个任务，应使用并发池。

错误策略也要提前定义：全部成功才算成功用 `Promise.all`；需要收集每项结果用 `allSettled`；允许快速失败时仍要取消不再需要的底层任务。并行只减少等待时间，不保证完成顺序。

### 发散 3：AI 生成的代码满足哪些条件才能合入？

**关联原题：第 3 题（日常 AI 工具使用）**

**参考回答：**

至少满足：需求与非目标一致；API 和版本真实；能解释关键状态与失败路径；覆盖空值、超时、取消、并发和销毁；无明显资源泄漏、安全问题和主线程阻塞；构建、lint、测试及真机验证通过；diff 没有无关重构或重复抽象。

最有说服力的面试回答不是列清单，而是准备一个“AI 给错—通过什么证据发现—怎样修复—增加什么回归”的真实案例。

### 发散 4：MCP Server 暴露写操作时，安全模型怎样设计？

**关联原题：第 4 题（Skill 与 MCP）**

**参考回答：**

按最小权限拆分只读与写工具；参数使用 schema 和业务白名单校验；文件路径、SQL、URL 等不能直接相信模型输出；删除、发布、发消息等不可逆操作要求显式用户确认；为每次调用记录操作者、参数摘要、结果和 trace ID；设置超时、速率、返回大小和幂等键。

模型“决定调用工具”不代表模型拥有最终授权。授权应由客户端、服务端和用户策略共同决定，敏感凭证也不能直接暴露进 Prompt。

### 发散 5：`map()` 是否等于不可变更新或深拷贝？

**关联原题：第 5 题（map 与 forEach）**

**参考回答：**

不等于。`map` 只创建新的外层数组，元素如何产生由回调决定：

```ts
const next1 = users.map(user => user);              // 元素仍共享原对象。
const next2 = users.map(user => ({ ...user }));     // 只浅拷贝一层。
const next3 = users.map(user => ({
  ...user,
  profile: { ...user.profile }
}));                                                // 复制发生变化的嵌套路径。
```

不可变更新的目标是让变化路径产生新引用，而不是无差别深拷贝整个对象图。真正深拷贝还要处理 Date、Map、循环引用和类实例，不能简单依赖 `JSON.stringify/parse`。

### 发散 6：为什么不建议在 `forEach()` 中增删数组元素？

**关联原题：第 6 题（forEach 修改数组）**

**参考回答：**

遍历开始时要访问的索引范围已经形成，而 `shift/splice/delete` 会改变后续元素所在索引。结果可能是某些元素被跳过，新增到尾部的元素也不一定会被遍历，代码很难推理。

过滤元素使用 `filter`；替换元素使用 `map`；确实需要原地删除时可从尾部向前使用普通 `for`；复杂批量变更则先收集操作，再统一应用。

### 发散 7：`LazyForEach` 的 key、`cachedCount` 和组件复用应怎样配合？

**关联原题：第 7 题（LazyForEach）**

**参考回答：**

key 应来自稳定业务 ID，不能用每次变化的随机值；列表可能重排时也不宜只用 index。`cachedCount` 决定可视区域外预创建/布局的数量，过小会增加快速滚动时临时创建，过大则提高内存和初始负担。

`LazyForEach` 解决“何时创建”，复用机制解决“能否重新使用已经创建过的节点”，二者不是一回事。复杂 Item 应减少 build 中的重计算和对象创建，并通过 Profiler 观察滑动帧率、节点数和内存后再调缓存。

### 发散 8：泛型在运行时为什么不能替代输入校验？

**关联原题：第 8 题（泛型）**

**参考回答：**

泛型主要是编译期约束，运行时收到的 JSON、数据库内容和 N-API 数据并不会因为写了 `Result<User>` 就自动成为合法 User。外部数据仍可能缺字段、类型错误或带恶意超长内容。

因此边界层需要显式解析与校验，成功后再转换成内部泛型类型；内部业务才能安全依赖类型系统。类型声明描述“我们期望什么”，运行时校验证明“收到的确实是什么”。

### 发散 9：怎样用状态矩阵避免组件 Spec 漏掉异常场景？

**关联原题：第 9 题（SDD + TDD）**

**参考回答：**

先列状态：初始化、加载、空、成功、部分成功、失败、无权限、离线、已销毁；再列事件：进入、刷新、重试、取消、重复点击、切后台、恢复和参数变化。对每个“状态 × 事件”定义下一个状态、UI、是否发请求和是否允许重复。

再从矩阵生成测试：合法转换验证结果，非法转换验证无副作用，异步测试覆盖乱序和晚到回调。这样比只按视觉稿列几个 Story 更能发现状态遗漏。

### 发散 10：MCP 能否自动解决组件库版本号问题？

**关联原题：第 10 题（组件文档 Skills、MCP、llms.txt）**

**参考回答：**

不能自动解决。MCP 只是传递资源和调用工具的协议；如果 Server 只提供 latest 文档，模型仍可能生成与项目版本不兼容的 API。

正确设计是让版本成为显式输入：客户端先读取项目 manifest/lockfile；MCP Resource URI 或 Tool 参数包含组件库版本；服务端只返回该版本的声明、示例和迁移信息；Skill 规定版本无法确认时必须停下来询问，而不是猜测。最终再用类型检查、构建和组件测试兜底。

### 发散 11：ViewModel 如何避免变成新的“上帝类”？

**关联原题：第 11 题（逻辑/UI 分离与 MVVM）**

**参考回答：**

ViewModel 只负责页面状态与用例编排，不直接承担网络实现、数据库 SQL、播放器底层细节和 UI 节点操作。把稳定业务能力拆到 UseCase/Service/Repository；把复杂状态拆成小状态机；一个 ViewModel 对应一个明确页面或功能边界。

判断标准包括：能否在没有 ArkUI 的测试环境中实例化；是否依赖 `UIContext`、弹窗或颜色资源；修改一个子功能是否总要改同一个超大类；是否存在大量互不相关字段和分支。出现这些信号时应按业务能力继续拆分，而不是再增加工具方法掩盖复杂度。

### 发散 12：为什么不应把 `UIContext` 做成全局单例？

**关联原题：第 12 题（Context 失效）**

**参考回答：**

`UIContext` 属于特定 UI 实例/窗口。全局静态持有会让其生命周期超过页面或窗口，造成旧窗口操作、内存无法释放、多窗口串用，以及异步回调在宿主销毁后继续调用。

更好的方式是由当前组件或页面在需要时注入；无 UI 依赖的逻辑层不持有 Context；确需跨层展示 Toast/路由时，定义窄接口并由当前页面实现；生命周期结束时取消任务和监听。缓存 Context 前必须先说明它由谁拥有、何时失效、谁负责清理。

### 发散 13：Worker/TaskPool 跨线程传递大数据时怎样减少拷贝？

**关联原题：第 13 题（Worker 与 TaskPool）**

**参考回答：**

先避免把整个业务对象图传到子线程，只传任务必需字段。对大型二进制数据，优先使用平台支持的可转移对象，把底层 buffer 所有权转移而不是复制；确需多个线程共同访问时使用符合平台约束的 Sendable/共享对象，并明确同步规则。

不能在转移后继续使用原 buffer，也不能把普通可变对象当作天然线程安全。还应分块处理超大数据，设置并发上限和取消信号，并用 Profiler 比较序列化、拷贝和计算各自耗时。对于 Native 媒体帧，更合理的方案通常是传句柄或让数据留在 Native 管线，而不是逐帧跨 ArkTS 线程复制。

### 发散 14：怎样证明闭包导致了内存泄漏？

**关联原题：第 14 题（闭包及风险）**

**参考回答：**

固定复现步骤，多次进入退出页面并观察停止操作后的内存是否回落；抓取前后 Heap Snapshot，查找未释放页面/组件实例，再沿 retaining path 查看谁仍持有它。如果路径是全局监听器或 Native 回调 → 闭包 → 页面实例，就有直接证据。

随后取消监听或将回调置空，在相同条件下重复测试，验证对象数量和内存曲线恢复。不能只凭“代码里有闭包”就认定泄漏，闭包本身正常，问题是它被长生命周期根对象持有且没有解除。

### 发散 15：Prompt Engineering 与 Context Engineering 有什么区别？

**关联原题：第 15 题（Prompt 与采样参数）**

**参考回答：**

Prompt Engineering 主要优化当前指令如何表达；Context Engineering 关注模型在一次任务中实际看到的完整信息，包括系统规则、仓库文件、检索结果、工具返回、历史对话、权限和 token 预算。

对于大型代码任务，失败往往不是一句 Prompt 写得不漂亮，而是缺少正确源码、给了过期文档、工具结果过长或关键信息被截断。因此应先设计上下文选择和验证链，再调措辞与采样参数。外部文档和工具返回还可能包含提示词注入，必须区分不可信数据与高优先级指令。

### 发散 16：两个依赖确实要求互不兼容的版本时怎么办？

**关联原题：第 16 题（鸿蒙版本冲突）**

**参考回答：**

先确认冲突是 API 不兼容还是仅 semver 范围过窄。若实际兼容，可推动上游放宽依赖范围并发布新版本；若确实不兼容，优先升级或替换其中一个依赖。

无法统一时可考虑在模块边界隔离版本、封装适配层、私有 fork 并修复，或把能力放进独立 HSP/进程/Native 边界；能否共存取决于打包方式、符号和运行时，不是所有库都支持多版本安装。`overrides` 强行统一只能用于经过兼容验证的情况，否则会把安装冲突变成运行时崩溃。

### 发散 17：为什么 LRU 通常使用“哈希表 + 双向链表”？

**关联原题：第 17 题（数组与链表的缓存差异）**

**参考回答：**

哈希表负责按 key 平均 `O(1)` 找到节点；双向链表维护最近使用顺序，并能在已知节点时 `O(1)` 删除和移动到头部。只有数组时，淘汰或移动元素通常需要搬移；只有链表时，按 key 查找要 `O(n)`。

工程版本还要考虑容量按条目还是字节计算、TTL、线程安全、淘汰回调和大对象析构。并发时哈希表与链表是一个一致性整体，不能各自随意加锁；回调最好移到锁外，避免锁内执行未知代码。

### 发散 18：JsBridge 如何做协议版本和向后兼容？

**关联原题：第 18 题（JsBridge 原理）**

**参考回答：**

消息包应包含协议版本、方法、请求 ID 和结构化参数；新增字段保持可选并给默认值，不能改变旧字段语义。Native 在能力协商阶段返回支持的方法和版本，Web 根据能力降级，而不是仅判断 App 版本字符串。

废弃接口要保留迁移窗口和明确错误码；回调支持超时和幂等；新旧页面与新旧客户端组合都要进入兼容矩阵测试。Bridge 日志记录方法、版本、耗时和错误码，但对 Token、用户数据和大 payload 脱敏。
